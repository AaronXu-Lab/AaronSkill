# 交互式流程画布工作流

本文为执行事实源，`workflow.svg` 为面向人的可视化投影。目标是在同一画布中并列操作真实 Modal、Sheet、Dialog，审查流程及分支，并用评论迭代可复用组件。画布挂在所属业务页面路由下，形如 `/<业务路由>/design-canvas`（如 `/login/design-canvas`），`?preview={name}` 单独走查一条流程的实际效果。此路由是 Step 1 的设计整理与评审工具，不是所属业务的正式页面；Step 2 仅在用户明确要求时，把已审阅设计接入 `/login` 等实际业务入口。

## 选择执行范围

沿用完整会话中的范围和授权。先读取项目约定、现有画布就绪记录及相关路由；不要以目录存在推断环境可用。

- **仅初始化环境**：进入 [初始化模块](initialization.md)，完成就绪记录与基础交互验收后交付，不自动设计业务。
- **新建或扩展业务画布**：快速核实当前环境能力；满足需求则跳过初始化，仅在缺失或失效时进入初始化模块补齐。随后执行下列业务阶段。
- **局部评论修改**：沿稳定节点 ID 定位相关组件、场景和入口，只读受影响资料；扩展状态、路由或隔离机制时才扩大检查。
- **应用到业务**：先核实用户是否已明确要求迁移，再进入 [评论与迁移模块](iteration-and-migration.md)。画布认可本身不构成迁移授权。

## 0. 前置：核实可复用的画布能力

先看现有画布的就绪记录、实际运行能力及项目清单／锁文件。局部评论或业务入口修改只核对受影响能力；现有画布能完成本次任务时直接沿用，不因依赖版本与参考实现不同而要求升级或阻塞。

- **新建或补齐基础设施**：优先复用项目已经安装且能满足隔离预览、布局、连线和交互要求的框架与库。`canvas-kit` 的 React、`@xyflow/react` 和 `elkjs` 是参考实现，不是固定技术栈或版本门槛；移植时按项目实际 API 适配。
- **确有能力缺口**：先确认现有依赖和项目设施无法满足；需要安装时按项目包管理约定选择兼容版本，说明目标包、许可、安装命令及锁文件变化，并在引入前取得所需授权。用户已明确授权本次依赖更新时直接执行，不重复询问。
- **无法引入必要依赖**：只暂停依赖该能力的画布实现；仍可完成业务建模、组件或实际入口中不依赖它的工作，不用不可靠的静态截图代替交互预览。
- 在就绪记录中写明本项目实际使用的依赖与版本，供复现和后续升级判断；版本不同本身不是失败。

`@phosphor-icons/react` 同样只是参考图标，可用项目现有图标替换。

## 1. 建立业务事实与覆盖模型

读取 [流程建模](modeling.md)。从实际路由、触发按钮、调用方、组件和条件追踪可达链路，记录正在使用、不可达旧代码及尚待核实的内容。不得仅凭画布枚举或文件名认定业务已覆盖。

产出入口—场景—组件—节点—边的覆盖表，并标注每条边画线或改为出口；每项标明证据、变更类别（新增、修改、复用）和期望行为。只纳入实际存在或本次明确要求的新状态，区分事实与提议。缺失事实时继续独立可做部分；仅阻塞依赖该事实的设计，不虚构分支。

## 2. 在就绪环境中实现与设计

读取 [组件预览与场景设计](component-design.md)。节点挂载实际组件，用场景参数和隔离适配承载不同状态；入口、判断、结果可用语义节点，无实际 UI 的节点不伪造弹窗。优先复用设计系统与已审阅组件。

节点位置由分层布局引擎按流程分区、主路径泳道和从左到右的边计算，手动拖拽只作微调；验收须满足连线指标，不满足时先精简连线和端口，不为指标或字号拆出更深层级的流程。新画布先复制 [canvas-kit](../assets/canvas-kit/) 再填流程数据：视觉以其 HTML 标准件为准，逻辑以 `reference/` 参考实现为准，项目有设计系统时用其组件与 token 实现同等效果；卡片、目录、视口与图例的规则见 [画布呈现](canvas-presentation.md)。实现覆盖模型中的交互与状态，校准内容高度、字段语义、步骤与操作结果。项目 Fake/演示规则适用时读取并使用可用的 aw-design-fake；中文 UI 文案适用时读取并使用可用的 aw-wording-reviewer。缺少这些 Skill 时沿项目现有规则执行同等范围的隔离或文案检查，报告未使用专门审查；不能建立可靠无副作用预览则停止运行该场景。

画布实现和验证属于设计请求范围；除非用户要求阶段评审，完成第一版后继续自查与修复，不等待默认确认。

## 3. 评论驱动迭代

读取 [评论与迁移](iteration-and-migration.md)。将评论绑定到稳定节点、场景和组件；修改后回读对应节点及其上下游，记录处理状态与证据。没有原生评论能力时可用项目内结构化记录承载，不强制安装协作服务。

将新增发现回填覆盖表，逐个核对实际业务场景和入口；不能只完成评论列表便宣布业务覆盖完成。

## 4. 验证与设计交付

按 [验收矩阵](verification.md) 执行受影响范围的浏览器交互检查及项目适用的类型、lint、构建或测试。新环境需完整基础验收，成熟环境局部设计只回归受影响能力。必要检查失败时修复并重验；若受环境、事实或权限阻塞，交付可用部分及明确未通过项，不宣称完成。

交付 `/<业务路由>/design-canvas` 与各流程 `?preview={name}` 入口、覆盖表、组件复用关系、评论状态和检查证据，说明未覆盖与未验证项。收尾清理本次验证创建的临时文件、命名浏览器会话和进程；保留正式画布、评论和验收证据。

## 5. 按授权迁移并验收

Step 1 的 `design-canvas` 只交付设计整理结果。若用户未要求应用到业务，到此完成当前范围；若明确要求迁移，Step 2 复用已审阅组件接入实际入口，按迁移模块处理状态编排与业务适配，再核对覆盖表和验收矩阵。迁移中发现新的生产副作用或范围外操作时仅暂停该动作，明确所需授权；完整会话已授权的内容不重复询问。

最终交付区分“画布设计已验证”与“业务入口已接入并验证”。画布通过不能替代真实入口验收。
