# 执行工作流

本文是执行事实源；`../docs/workflow.svg` 及诊断子图展示主要阶段。macOS 按目标网站分数持续优化，Android 沿用既有四块流程；下方四块提供可选措施及验证方法，实际案例见 [执行结果](results.md)。节点名称、分数和设备设置是案例值，执行时读取本机现状并采用用户本次选择。

## 按目的选择独立分支

| 目的 | 入口与完成标准 |
| --- | --- |
| Claude 数据清理 | 读取 [清理分支](workspace-cleanup.md)，沿用限定范围、扫描清单和选择流程；只扫描请求交付清单即结束 |
| macOS 诊断与优化 | 先执行下方 macOS 优化循环，再按四块选用措施；交付当前约束下经过验证的最佳配置及停止依据 |
| Android 诊断与优化 | 沿用下面四块：完整前测、只读诊断列项、获准执行、完整后测与相关检查、交付或恢复 |

清理与诊断优化分别授权。单纯解释检测项或只读诊断时，交付当前范围的说明与证据。

## macOS：以目标网站分数持续优化

本节仅适用于 macOS。目标是尽可能提高用户指定网站的真实检测分数，直到当前授权、可用节点和设备条件下没有有证据支持的可行提升路径。默认以 IPKK、Net.Coffee、CLIS 三站分数与诊断项共同评价；用户明确缩小范围时沿用其选择。四块措施是诊断工具，不是必须全部执行的清单；不能把完成一次修改、脚本成功或首次涨分当作任务完成。清理和 Android 不进入此循环。用户只要求解释、诊断或修改 Skill 时，完成相应交付，不执行本机网络优化。

### 先确定要更新的配置

只读核对 ClashX Meta 配置列表、订阅登记、本地文件及实际运行状态，区分可选配置、活动配置、订阅原始输入、生成文件、overlay 与备份；备份和临时文件不算独立候选。列出每个候选的名称、绝对路径、来源类型、是否活动及已有更新方式，隐藏订阅凭据。

存在多份可更新配置且用户尚未明确选择时，必须询问更新哪份，不能默认选择活动配置、XSUS 或全部配置。等待期间可继续只读诊断；选定前不写配置、不运行更新器。已有明确选择直接沿用。只有一份时记录识别结果并继续。目标不是活动配置时，先准备候选；真实前后测需要激活目标，激活未获授权时说明此缺口，不拿另一份配置的检测结果证明目标效果。

### 活动配置与业务连接的一致性证据链

诊断、修改前测和每次安装或订阅更新后的验收，都按**本次选定且实际活动的配置**建立同一条证据链；目标尚未激活时仅做静态候选检查，不声称完成核心与连接验收。记录配置名称与绝对路径、当前文件哈希、来源订阅、对应 overlay/更新 `.command` 的输入输出和重载目标；检查它们是否确实绑定同一配置。另一份配置中的规则、节点或历史执行结果只能作为对照，不得推定为活动配置已具备，也不得未经授权跨配置迁移。

针对本次要验证的服务和应用，从实际域名、进程名与可执行文件路径出发，逐层核对：①活动 YAML 及持久 overlay 是否分别覆盖目标域名和应用进程/路径，应用规则的匹配范围与路径正反例是否正确，服务及应用规则是否位于会抢先命中的宽泛规则之前，引用节点在当前配置中是否存在；②核心 API 或已加载配置是否包含预期规则及顺序，不能仅凭磁盘 YAML 或合并脚本成功判断已生效；③分别由网页和目标原生应用产生新的正常业务连接，读取连接的进程名/路径、命中规则、策略组和最终节点，并与获准预期比较。若客户端/API不能暴露某层，记为“未验证”及原因，不把上一层证据当成下一层通过；不能用网页连接代替原生应用验收。修改后和订阅刷新后都重新完成相关层的核对；更新器还需证明重放后的活动文件、overlay、入口和核心状态一致。

把 STUN/WebRTC 候选、DNS 解析路径、检测网页出口与 Claude 等业务请求出口分别记录。仅有 STUN→美国的规则不证明 Claude/Anthropic 业务流量也走美国；网页分数、DNS 标签或另一配置中的业务规则也不证明当前业务命中。域名规则命中只证明该域名的分流，不证明应用进程/路径兜底曾触发。核心连接 API 缺少进程字段时，可将同一时间窗的系统 socket、PID 与可执行文件路径关联留证，并明确关联证据的限制；没有实际触发兜底的连接，就把兜底运行验证标为“未触发”，不能记作通过。

发现目标服务或应用规则缺失、顺序错误、节点不存在、overlay/入口错绑或实际命中不符时，先核对本次完整会话的授权。若已授权修复选定目标应用、出口节点和配置，缺失规则及其持久化属于该修复范围：补入活动配置对应的 overlay 与更新 `.command` 合并契约，核对应用 bundle 内实际进程/可执行路径的正反例、规则优先级及节点引用，再经隔离合并、核心加载与目标原生应用新连接验收；失败则修复重验，无法恢复正常路径时回滚并报告。不能只列出缺失项便结束获准修复。纯只读诊断只报告缺口，不自动写入；真正增加未获授权的应用、配置或出口范围时，再按下方许可边界确认。

### 基线、假设与每轮对照

使用下方共同入口取得完整基线、业务连通性和上述一致性证据链。建立候选清单：当前扣分项、证据、可能原因、预期收益、具体改动、授权范围、验证方法及可恢复状态。优先处理可一次修正且证据明确的问题；历史案例不限制新假设，也不证明其适用于本机。必要时核对目标站点当次可观察的计分规则。

沿用已有具体许可；用户授权的一组调整及其明确范围内的重复测试可连续完成，不每轮重复询问。新增影响范围、未授权的出口/应用变化仍按共同入口处理。每轮从已验证最佳状态出发，只改变一个因素或一组不可拆分的关联设置，备份后校验、安装，完成同浏览器的新一轮完整扫描与正常路径验收。记录每轮配置哈希、改动、全部分数/标签/出口、业务结果及决定。

初次改善要在同条件下再完成至少一次完整扫描，和基线或当前最佳状态的重复结果比较；若波动掩盖差异，做回切对照并保留全部结果，不挑最高一次当作稳定收益。可重复涨分且正常业务验收通过才提升为最佳状态。同分但修复了已证实问题的变更可在获准目标内保留，明确标为“无分数提升”；无效或退化候选恢复到最佳状态，按第四块检查恢复。若最佳状态自身已失效，恢复最近可验证的安全备份并报告，不能声称最佳结果仍有效。

### 三站优化评价体系

macOS 默认使用 **IPKK、Net.Coffee、CLIS**，开始优化前读取 [三站评分与证据边界](diagnostic-tools.md)。建立三站各自的完整基线，正式候选后测及最终验收也记录三站分数、扣分项、出口和完成状态。过程中的单项诊断可只查相关路径，但未完成三站复测的候选不得称为三站最佳。清理与 Android 保持原流程；MoreTools 和 IPinfo.CV 不纳入本评价体系。

三站形成并列评分记录，不求和、不平均、不跨站换算。每个站点只与自身在同浏览器、相近时间、同出口选择和相同完成条件下的结果比较；更换浏览器或评价站点后重建相应基线。第三方“Claude 信任分”不是 Claude 官方评分，不能证明账号风险或实际业务权限。记录原始分数，不自行扣除误判项后制造“修正分”。

最佳状态的判定以正常业务验收通过为前提：至少一站可重复提升，其他站未出现经核实的退化，才作为整体改善；三站同分但修复了已证实问题，可按既有许可保留并标为无分数提升。一升一降时先检查差异项、原始 IP、协议、域名、时间、数据源、请求状态与核心分流；剔除误判的影响只用于解释，不改网页分数。确认是真实取舍且用户未给优先级时，保留此前已验证最佳，报告候选对照并询问取舍，不擅自选最高一站或用平均分掩盖退化。

区分“出口是否相同”“是否符合用户预期分流”“是否属于站点可用地区”。STUN 覆盖不同，某站通过不能覆盖另一站已观测直连；只按证据修复，不为凑分封锁检测服务器、禁用正常功能或统一有意分开的出口。公网候选排除未指定、回环、私网、链路本地地址及 mDNS 名称；没有候选、超时或字段缺失记未知。数据库或启发式标签不能覆盖真实链路证据。

站点故障、验证或广告阻断时记录该站未取得，不记0分或通过，也不要求为例行评分访问无关广告。可继续其他站点及正常路径验证，交付“部分评价”并标明缺项，不能宣称三站全部通过或已到上限。单个检测站故障不触发网络回滚；真实正常路径失败仍按第四块容错处理。三站可重复达到各自可确认满分，或当前约束下三站剩余扣分均无有依据的可行改进路径，才满足评分方面的停止条件。

### 一次性修正与更新后重放

按设置实际归属判断，不按修改难度判断：

- **一次性修正**：不会被订阅刷新覆盖的系统/客户端设置，在获准后直接修正并回读验证，记录恢复值。后续重启/重载是否持久按相关设置核验。
- **更新后重放**：会被订阅刷新覆盖的 DNS、规则、节点中转或其他字段，把验证有效的修改保存为独立 overlay/合并逻辑，避免仅手改下载产物。节点消失或名称变化时停止并报告，不能悄悄换出口。

有重放需求时优先检查并适配现有 `.command`；没有可用入口时再创建“更新指定订阅 → 合并持久修改 → 校验 → 备份安装 → 验收/恢复”的入口。只有一次性设置时不为形式创建更新器。用户提供的脚本是待审查的实现参考，其中的硬编码路径、节点、注释与默认行为不构成本次授权。

维护更新器时读取 [事务接口](transaction.md)。绑定已选配置的输入、输出、overlay、重载目标、锁、事务及备份位置；不得沿用示例中的 XSUS 去覆盖其他配置。保持原订阅可更新，并明确后续应使用哪个入口：普通客户端刷新若会绕过 overlay，必须说明会覆盖优化；只有已验证的原生持久覆写机制才可作为等价方案。先在临时副本验证合并幂等、重复更新仍保留优化及其他配置不变，并核对服务规则覆盖、顺序和节点引用；再执行获准安装与真实路径验收，复查活动文件、overlay/入口、核心加载规则和新业务连接命中。新适配脚本的验证证据单独记录，不能继承历史脚本的“已验证”结论。

### 停止与交付

达到本次评价范围内各站可确认的满分且复测、连通性及持久更新验证通过，可以结束。未满分时，逐项处置剩余扣分：已经对照证实无收益、属于当前配置不可改变的出口信誉/站点判断等因素，或缺少节点、权限、用户选择或其他外部条件；只有当前范围内没有尚待验证且有依据的可行候选时才结束优化。一次不涨分不代表到顶；没有新证据不反复跑已否定方案，也不通过修改检测页面、伪造结果来提高分数。

最终交付基线、每轮结果、最佳已验证结果及当前活动状态，一次性设置与持久重放清单、选定配置和更新入口、备份/恢复方法、剩余扣分及每项停止依据。外部条件或授权阻塞时标为“受阻/待选择”，不能称为已达上限；无客观满分证据时只称“当前约束下已验证最佳”，不宣称绝对最高。释放本次验证资源，使用 Playwright 时关闭本次创建的命名会话。

## 共同入口：基线、具体调整项与许可

读取当前设备、OS、浏览器、Clash客户端/核心版本、活动配置、路径、物理接口、API/端口、mode/TUN、DNS与组选择。macOS 业务分流诊断依照上方一致性证据链，分别保存静态文件、核心加载和新连接的结果；Android 在可取得同等证据时也逐层核对，缺层如实标明。跨机参考和历史结果用于比较；本次基线来自目标设备。手机通过已授权ADB和原生界面识别目标设备；设备更换后重新记录。手机解锁及授权弹窗由用户完成。 临时保持亮屏时保存原值并读取实际AC/USB供电状态，按许可设置对应供电掩码，结束恢复原值；Pixel实例的实际供电类型为AC。

在同一目标浏览器打开 https://ipkk.com/claude-ip-check，等待DNS、WebRTC等结束、扫描按钮恢复。Mac使用真实Safari；Android使用手机实际Chrome。记录时间、版本、完成状态、分数、风险标签、网页/Cloudflare/Claude/DNS/UDP出口及地区、时区和业务结果。没有有效结果时写“未取得”及原因；沿用已执行的前测许可流程后再决定安装。

正常网络基线使用Apple、Cloudflare、Claude、ChatGPT四目标，记录curl退出码、HTTP及DNS/TCP/TLS/总耗时。分流预期分别记录普通出口和业务出口。页面源码核对与核心连接采样已用于解释扣分：IPKK的WebRTC比较参照是站点网页出口；代理出口不同与此前出现本机公网候选分别记述。剩余代理、滥用及字体标签作为页面实际观察值记录。

按本次需要列出具体调整项：现状、证据、动作/值、影响、文件或设置、验证及恢复方式。沿用完整会话中对相同具体项目的明确许可；新增应用或改变出口选择另列项确认。获准后完成对应实现、验证与修复，验收条件提前写入记录。

## 1. 网络接管与 DNS

### 已执行的操作

- **Mac接管核对**：读取Rule模式、gVisor TUN及UDP/TCP53劫持；区分系统DNS和核心业务DNS，核对实际加载的配置与连接。
- **Android接管调整**：关闭Allow Bypass和附加System Proxy；Append System DNS设为Disabled；核对VPN、DNS劫持、应用接管范围与实际浏览器出口。
- **业务DoH**：使用Cloudflare/Quad9有效RFC8484查询验证答案，再设置nameserver/direct-nameserver及代理绑定。节点引导解析保留并单独核对。Mac同步实例的DoH经日本02，CN/Apple/Figma直连解析策略使用223.5.5.5/doh.pub；手机实例的业务DoH经美国09，清空业务policy并移除fallback。
- **STUN分流**：读取当次实际STUN域名及解析地址，给已观测域名和精确地址添加获准节点规则，核对UDP能力、核心连接和浏览器候选。
- **单解析器对照**：生成仅Quad9候选，保留其他设置，安装后完整重测；该案例标签继续波动，按原备份恢复双DoH并核对文件及联网。

### 已采用的验证方法

DoH检查事务ID、rcode和答案；核心连接验证真实内部解析器路径。网页显示的递归解析商与配置的DoH端点分别记录，实例中出现过Google/Cloudflare标签变化。

连接异常时使用正常TUN、显式HTTP CONNECT、绑定物理接口且TUN关闭的隔离核心作对照，保存每次时间与路径。超时预算使用连接12秒、单请求20秒；curl35按TLS握手失败留证，同轮其他目标和后续对照作为独立结果。

用户曾要求的Type64/65只读检查：对实际业务域名查询A/AAAA/SVCB/HTTPS，与公共DoH答案对照，再关联Safari trace和核心规则/代理链。该实例当前Fake-IP路径的64/65为空答案，采样业务连接走美国09；结果见 [执行结果](results.md#只读诊断记录)。按请求复用此已执行的查询与关联流程。

## 2. 应用分流与中转

### 已执行的分流

| 范围 | 已执行措施 | 验证方式 |
| --- | --- | --- |
| Claude/Anthropic/OpenAI/ChatGPT域名 | 服务规则直接指定获准美国节点，置于宽泛规则前 | 手机/电脑trace、实际出口与核心规则 |
| Safari/WebKit境外流量 | `AND`组合WebKit进程与`NOT GEOSITE cn`，放在既有服务/DIRECT规则之后、订阅规则之前 | Safari完整检测及WebKit进程的真实连接 |
| Claude Desktop目录 | `PROCESS-PATH-REGEX`匹配标准Claude.app目录，指定获准美国节点，同样保留既有规则优先级 | 路径正反例、核心配置及ProcessPathRegex加载 |
| 指定美国节点的中转 | 节点级`dialer-proxy`指向获准日本节点 | 节点引用/循环校验、核心元数据和真实请求 |
| 手机普通日本、业务美国 | 普通组日本08，15条Claude/ChatGPT等域名规则美国09 | 原生选择界面、VPN重启后的浏览器出口 |

WebKit实例规则为：

```yaml
- AND,((PROCESS-NAME,com.apple.WebKit.Networking),(NOT,((GEOSITE,cn)))),🇺🇸 美国 09 家宽
```

Claude Desktop实例规则为：

```yaml
- PROCESS-PATH-REGEX,^(/Applications|/Users/[^/]+/Applications)/Claude[.]app/Contents/.*$,🇺🇸 美国 09 家宽
```

实际合并保留AXO规则与Fake-IP排除，普通节点、GLOBAL和其他Selector按备份恢复并核对。Mac美国09/07经日本02，普通日本08和GLOBAL日本07；这些是该实例的用户选择。下一次按已确认的目标节点、应用和规则优先级生成候选。

验证结果标明等级：实际应用连接、浏览器结果、路径匹配或核心加载。每次分流变更以当前活动配置的域名及应用规则覆盖、顺序、节点存在、核心加载及对应应用新连接命中验收；仅路径匹配或核心加载不能升级为实际业务验证。Claude Desktop此次证据为目录表达式匹配和核心加载；WebKit、业务域名和手机分流有真实路径证据。详细计分记录位于 [执行结果](results.md)。

## 4. 持久更新与验证

### 持久文件与安装

Mac按上方分类处理一次性设置，并将需重放的获准设置写入所选配置的overlay，通过对应更新入口合并；`ADJUST_RULE`与`XSUS.yaml`仅为历史实例。Android把导出配置经合并脚本生成独立File配置，再通过客户端导入、保存和激活。手机原URL订阅及优化File均作为恢复点保留，File配置的来源与合并输入记录在交付中。

实施前备份本次涉及的YAML、overlay、脚本与运行/偏好状态，记录SHA-256、mode/TUN和全部组选择。私有目录0700、敏感文件0600、活动脚本0700。运行已执行的zsh/Python/Ruby与核心校验、引用和路径规则检查、隔离DNS及节点预查，再原子安装并核对运行配置。

Mac通过客户端原生重载、运行API和已编译配置核对DNS/节点/规则，保留TUN与各组选择。再次核对活动文件与对应 overlay/更新入口的绑定、目标服务和应用进程/路径规则及优先级、节点引用，以及网页和目标应用各自新连接的实际命中；订阅刷新后重复这些检查，缺失项不得称为已持久化或已验证业务分流。Android在客户端激活File配置、恢复获准节点，再通过VPN重启验证选择持续生效。导入默认自动组、惯性滚动误选等过渡阶段单列，最终结果来自纠正后的新连接。

### 真实路径与前后记录

在同一目标设备浏览器完成后测，保存实际分数、标签和出口；每轮等待扫描按钮恢复。回滚后检测独立记录。Mac持续探测为正常TUN四目标；Android真实Chrome的测试页/trace证明正常VPN路径，ADB转发到手机HTTP代理的多轮检查标为辅助路径。

核对当次业务HTTP结果和预期分流。403/429与TLS35按对应层次留证；显式代理成功不覆盖正常TUN失败。页面分数与实际业务结果分别交付。

### 有限容错验收

验收前保存本次策略。当前已经实现并验证的默认值：

| 条件 | 动作 |
| --- | --- |
| 观察时长 | 至少300秒，逐目标保存正常路径结果 |
| 单轮失败且在以下上限内 | 保存首次错误和对照，继续原路径观察 |
| 连续失败达到3轮 | 回滚 |
| 已观察至少10轮，累计失败轮比例超过10% | 回滚；分母为正常路径完整轮次 |
| 持续观察及Safari确认结束 | 固定60秒窗口内取得连续3轮四目标成功 |
| 最终窗口耗尽或达到回滚阈值 | 恢复备份并检查联网 |

失败计数贯穿持续观察和最终窗口，窗口不重新计时；单请求无内部重试，正常请求及CONNECT对照受剩余预算限制。用户明确选择其他阈值时，执行前保存具体值与许可。加载前使用最多3轮有限基线检查，全部尝试留证。

### 恢复、收尾与交付

本地进程承担监测和自动回滚；Safari事务按当前ID、PID、stage和配置SHA核对后作决定。恢复文件后核对哈希、实际规则、mode/TUN和Selector，使用相同正常网络路径确认恢复。

交付写清已执行项目、验证等级、前后分数、失败轮数/比例/最长连续失败/最终连续成功、恢复状态、备份与活动文件位置。“观察时长”与含等待人工确认的总时长分开记录。已恢复的偶发失败按本次容错条件交付，具体原因按已有证据说明。

恢复手机临时亮屏原值，移除自建ADB转发，删除手机Downloads中的本次敏感导入/导出副本；关闭本次验证标签，保留用户原有页面。临时目录中的有价值记录提醒用户备份。
