# Component Review & Maintenance

本文定义审查与编辑两种模式的路由、执行顺序及完成边界。[workflow.svg](workflow.svg) 是面向人的语义概览。

## Input & Scope

先区分任务模式。审查模式用于设计基本完成的桌面 Web 或桌面应用界面、流程说明、设计稿或对应实现，判断组件为什么适用及如何被使用。仅要求颜色、尺寸、间距等视觉调整时不启动本审查；混合请求中只处理明确涉及组件语义的部分。

用户要求“编辑模式”，或维护组件规则、增删/同步索引、调整 Reference 时，进入编辑模式，读取 [编辑工作流](editing.md)。组件实现的变化是维护依据；单纯请求 Review 不授权自动更新规则。混合请求分别按用户授权完成两类产物。

## Identify & Load

两种模式都先读取 [组件索引](../references/components/index.md) 定位目标。审查模式按用户操作、状态、选择、导航或内容结构识别组件，再确认名称与 Gallery ID。一个 Panel 对应一份 Reference；结构型子组件仍随父级语义单独识别。

审查模式只加载本次涉及的 Reference。遇到选择边界不明确时，按其 Similar & Easily Misused Components 中的相对链接补读必要的候选组件。不要为了完整性预加载无关家族；索引以外的元素记录为当前规则尚未覆盖，不强行套用最相似外形。

## Review Mode

依次判断 `Semantics → Context → Differentiation → Composition → Internal Usage → Examples`：

1. 从 Definition & Semantics 确认核心职责，说明当前区域需要该职责的原因。
2. 以 When to Use / When Not to Use 核对场景条件；再通过 Similar & Easily Misused Components 区分相似组件。
3. 以 Composition 检查组件之间的职责、作用范围与层级。组件内部的 Label、Icon、Value、Trigger 和 Action 则按 Internal Usage 判断是否表达同一意图。
4. 用 Examples 澄清边界，不把一个案例扩张为所有业务场景的禁令。

用户当前明确要求优先。实际实现与 Reference 不一致时，核对当前组件公开实现、类型、相关 Gallery 和适用 Scenario；保留差异，不静默修改规则或产品来制造一致。ADM 历史调用只能说明场景存在，不能独自证明推荐用法。外部资料只在确有证据缺口时补读，并区分成熟语义与本地能力。

## Editing Mode

按 [编辑工作流](editing.md) 核对最新正式注册与实际变更，处理目标 Reference、索引及受影响入链。成员资格依据 `NAV_GROUPS` 的 `general` 与 `composite`，不能把当前索引数量当成永久范围；展示名变化与 Gallery ID 迁移分别处理。

编辑工作流是增删改、元数据和维护验收的规则事实源；仅在编辑模式加载。维护时不将产品界面 Review 作为前置条件，也不顺带修改 Gallery 或组件代码。

## Ambiguity & Recovery

静态设计无法证明点击结果、选择生效时间或控制范围时，将相关结论写为条件判断，不能把缺少交互证据直接判成错误。资料缺失时继续审查已明确的部分；仅当缺失信息会改变核心组件语义且无法合理判断时，提出一个聚焦问题，保留依赖该答案的结论。

只读审查不包含自动修复、更新 Reference 或修改其他项目。用户已授权局部修改时，沿用该范围完成修改及相称验证；没有必要重新取得同一授权，也不扩展到组件库发布或无关实现。发现检查失败时修复授权范围内的问题，无法修复的部分明确记录原因。

## Output & Completion

编辑模式按编辑工作流交付实际增删改结果、当前覆盖数、适用校验及待定差异。以下为审查模式的交付边界。

交付聚焦于组件选择与用法的审查结果：说明具体位置、观察到的事实、适用规则、为什么影响判断以及最小调整建议。满足条件的组合予以保留；需要确认的条件与已证实的问题分开说明。没有问题时直接说明范围内未发现语义或组合问题。

完成标准是用户指定范围内涉及的组件均经过适用维度判断，主要相似边界已核对，结论有可追溯依据，并说明仍需确认的条件。不默认运行前端全量构建，不扩展为通用可访问性、键盘、内容设计或视觉审计。只有这些内容改变组件语义或选择时才简要纳入。
