# 组件 API 设计约束

在编写 Gallery 示例前使用本约束审计目标组件。它不是要求所有组件采用同一套 prop，而是保证公开契约能准确表达组件自身语义，并能被独立验证。

## 1. 从使用意图建立 API

- 先确定组件的常见任务、默认用例和必须支持的差异，再命名 props。
- 公开轴必须对应用户或消费方能理解的概念。优先使用领域语义，如 `placement`、`selectionMode`、`density`；不要为了套模板强行添加 `variant` 或 `size`。
- 视觉处理、尺寸、内容、状态和行为应保持正交。改变一个轴不应静默改变另一个轴，除非二者在组件语义上不可分割。
- 对相互排斥且带条件字段的模式，优先使用枚举或可辨识联合，而不是多组可能冲突的布尔值。
- 避免“布尔汤”：当多个 boolean 组合产生隐含模式时，把模式提升为有名称的 prop；真正独立的开关仍保持 boolean。

## 2. 默认值和确定性

- 可选 prop 应有可追踪的有效默认值：来自参数默认值、primitive 默认值或明确文档。不要让 Gallery 猜测。
- 默认值应代表最常见且最安全的组件用法，而不是某个产品的品牌、语言、URL、资产或业务状态。
- 默认内容属于公开 API。库组件优先中性文案或无内容，由消费方传入本地化与品牌资源。
- 时间、随机数、网络、全局 store 或环境变量不得成为基础渲染的隐式前提。需要时通过 prop、adapter 或显式 provider 注入。

## 3. 状态与事件

- 受控与非受控 API 使用目标框架或底层 primitive 的惯例；两者存在时应成对且语义一致，例如 `value` / `defaultValue` / `onValueChange`。
- 不在 wrapper 与底层 primitive 之间维护两份竞争状态。
- 事件名描述消费方观察到的结果，payload 使用稳定的公开类型，不泄漏内部 DOM、store 或业务 DTO，除非平台惯例要求原生事件。
- 将 `disabled`、`readOnly`、`loading`、`invalid` 等状态分开，只有组件语义确实相同时才合并。
- Gallery 为了确定展示而设置的 `defaultValue`、`open` 或 fixture 只属于示例初始状态，不能被描述为组件 API 默认值。

## 4. 内容、slot 与组合

- slot 以角色命名，如 `leading`、`trailing`、`description`、`actions`，不要以临时布局位置或某个产品模块命名。
- `children` 或渲染 slot 是内容能力，不是 `ReactNode` 这样的展示轴；Gallery Caption 应写人能理解的 API 概念和值，例如 `content: text, icon + text`。
- 简单 native 行为优先透传合适的原生 props；组合 primitive 时保留其键盘、焦点和 ARIA 契约。
- 透传 `className` 或项目约定的样式扩展入口，但不要要求消费方靠覆盖内部选择器才能完成正常布局。
- 不把业务路由、服务调用、翻译函数、全局状态或品牌资源硬编码进可复用组件；通过语义 props、slot 或 adapter 隔离。

## 5. 可访问性契约

- 纯图标交互必须获得可访问名称；如果无法可靠推导，应要求消费方提供。
- 键盘操作、焦点顺序、焦点可见性和禁用行为应与底层控件语义一致。
- 错误、选中、展开和忙碌状态不仅依赖颜色表达，并暴露正确的语义状态。
- 组件需要 label、description 或 error 关联时，API 应让消费方能够建立关系，而不是由 Gallery 伪造静态标记。

## 6. Gallery 接近度检查

以下任一情况意味着 API 和 Gallery 已经离得过远：

- Caption 需要使用实现类型名或内部状态名才能解释组件；
- 两个示例看似比较一个 prop，却必须同时改多个不相关 props；
- 默认示例只能靠隐藏 wrapper、私有 CSS 或产品 store 才能成立；
- prop 组合存在冲突但类型允许，Gallery 只能挑选“碰巧可用”的组合；
- Gallery 展示的默认值与组件运行时默认值不同；
- 组件需要业务数据形状，而自身只消费其中少量 UI 字段。

若任务授权 API 修改，先用最小改动修复根因，并更新范围内调用点。若未授权，区分：

- **可诚实展示的债务：** 在交付说明中记录，Gallery 仍按真实契约展示。
- **会造成误导的缺口：** 停止该部分 Gallery，实现前请求 API 决策或授权。

## 7. 改动检查

API 改动后检查公开导出、类型声明、真实调用点、测试和文档。搜索旧 prop 名与不再有效的组合。不要为了兼容而永久保留两套语义冲突的 API；是否保留迁移层由目标仓库的版本策略决定。
