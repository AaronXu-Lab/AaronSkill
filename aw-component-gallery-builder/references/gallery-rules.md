# Gallery 展示规则

这些规则保留组件展示的默认基线、按轴组织和中性内容原则，同时不假定任何特定项目、文件路径或 UI 框架。

## 1. 复用本地展示语言

- 已有 Gallery 时，先检查结构最成熟的组件区。复用其 Section、Caption、示例舞台、行列布局和交互容器。
- 把成熟区当作结构参考，不把它的专属 prop 名复制给其他组件。
- 若项目已有 `PanelRow`、`Caption` 或同义 helper，优先复用；从零建立时才创建最小等价 primitive。
- 保留能让示例更清楚的 helper，删除只服务于产品故事、品牌或复杂 fixture 的 wrapper。

## 2. 组件命名

- 用户可见的组件名称写成自然标题词，例如 `File Explorer Tree`、`Sidebar Item Actions`、`Workflow Job Status Badge`。
- 代码符号保持项目语言的命名惯例，如 PascalCase；section id、URL anchor 和测试标识沿用项目现有格式。
- 只调整 Gallery 中的可见名称，不因展示需要重命名组件符号或公开导出。

## 3. 中性默认内容

- 通用文本优先使用可见内容 `Text`。
- 通用数字优先使用 `42`。
- 通用图标槽优先使用项目已有的 `Placeholder` 图标或等价的中性占位图形；不要新增品牌资产。
- Caption 优先写 `prop=value` 或 `prop: value1, value2`，避免仅用散文标签。
- 默认示例保持最小，只放足以理解外观和交互的内容。没有比较需要时，不增加固定宽度 wrapper。
- 只有组件契约本身要求时，才保留特定标签、图标、数量或多条 item。

## 4. `default` 是完整 API 基线

- `default` 放在组件 section 第一行。
- Caption 列出该基线涉及的所有主要公开展示轴及其有效默认值，包括 JSX/模板中省略、但实现实际采用的默认值。
- 按主要视觉轴、内容轴、状态/行为轴的顺序列出，例如 `variant=underline`、`itemWidth=0`、`content=text`、`badge=false`。
- 只有示例必须固定选中、展开或输入状态时才显式设置 `defaultValue` 等初始值，并清楚区分“样例初始状态”和“组件 API 默认值”。
- 默认值必须依据实现、公开类型或底层 primitive 契约验证，不能只依据旧 Gallery。

## 5. 每行只展示一个轴

- 组织顺序为 `default`，随后每个主要 prop/API 轴一行，例如 `size`、`variant`、`type`、`state`、`active` 或 `countType`。
- 轴名使用真实公开 prop 或正式 API 概念；Caption 展示 API 值，不展示 `ReactNode`、内部 enum 类型名或 CSS class。
- boolean 轴固定按 `false, true` 展示。启用态可用 `42`、图标或文本让差异可见，但 Caption 仍描述 boolean 开关。
- Caption 值和渲染示例必须数量相同、从左到右或从上到下顺序一致，每个值有一个可识别示例。
- 数字、宽度、尺寸或密度比较中，所有非目标内容保持相同，使目标轴成为唯一变量。
- 不把无关状态合并到同一行。组合态只有在组合本身是重要、正式的 API 用例时才单独展示。

## 6. 比较方向和间距

- 紧凑控件在自然尺寸下不会拥挤、换行或失去辨识度时，使用横向行布局。
- 宽组件、整行组件或内容密集组件并排后会压缩有效宽度或使顺序不清时，使用纵向布局。
- 纵向比较中的每个示例保持相同且有意义的宽度，确保只有目标轴变化。
- 比较项保持相邻、紧凑，使用 Gallery 的自然 gap。不要添加 `space-between`、全宽增长、任意 spacer 或把小型对比推到舞台两端的 wrapper。
- 需要边界、滚动、溢出或响应式语境时，使用明确命名的测试舞台，并让其尺寸服务于该组件行为，而不是装饰布局。

## 7. 从零建立 Gallery

从零模式先建立最小运行骨架：

1. 使用项目现有入口、框架、样式系统和 Token。
2. 创建稳定的组件 section 与可链接 id。
3. 创建 Caption 和示例舞台/行布局，支持横向与纵向比较。
4. 当设计系统已有主题或背景语义时，提供对应主题/背景检查；不要自行创造第二套主题系统。
5. 为交互组件提供局部状态容器，使事件和受控/非受控行为可以操作。
6. 组件数量产生明显查找成本时再增加分类、导航或搜索；小型 Gallery 不需要文档站壳。
7. Gallery shell 本身必须响应式、键盘可用，并避免遮盖组件的 focus ring、浮层和 overflow 行为。

不要把产品路由、真实账户数据、网络请求或业务 store 作为 Gallery 的运行前提。复杂业务对象先映射为组件真正需要的中性 UI 形状。

## 8. 保持真实产品用法独立

- Gallery 使用中性 `Text`、Placeholder 和 `42`；产品页面继续使用适当的真实文案、图标、数量和业务类型。
- 仅 Gallery 重排时不修改产品调用点。
- 组件 API 变化时才更新真实调用点，并扫描废弃 props、旧 Caption 和不再有效的 fixture。

## 9. 完成审计

- 每个可见组件名称是否自然分词？
- `default` 是否列出该面板主要有效默认值？
- 每个轴是否使用真实 prop/API 名称？
- boolean 是否按 `false, true` 展示？
- Caption 与示例是否一一对应且顺序一致？
- 横向/纵向选择是否符合组件实际尺寸？
- 同轴比较是否足够接近，且只改变目标变量？
- 示例是否摆脱品牌、业务和产品 fixture？
- 交互、主题、焦点、浮层和响应式行为是否在需要时可检查？
