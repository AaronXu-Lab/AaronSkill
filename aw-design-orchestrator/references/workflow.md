# 设计流程编排

本文是执行事实源，[流程图](../docs/workflow.svg) 为人类概览。负责调用、交接和推进已有 Skill，具体设计判断由相应 Skill 承担。第一版只串联主流程，不加入按需增强、并行代理、模型分档或自动调度服务。

## 入口分流

- 用户在调用本 Skill 时以 `/help` 作为命令，或在明确的本 Skill 上下文中单独发送 `/help`：只读 [帮助](help.md) 并回答，随后结束本次帮助请求。不调用业务 Skill、不研究竞品、不检查项目、不安装依赖、不新建或修改进度文件，也不推进正在等待的阶段。附带需求时仍只展示帮助；需求留待用户明确开始。
- `/help` 出现在引用材料、代码、竞品地址或需求正文中，不视为命令。不接管其他工具的同名命令。
- 正常输入：接收 PRD、文件/链接、模糊想法、竞品体验地址或产品名称及其组合，进入设计塑形。不要求先填写完整 PRD。
- 用户明确要求继续：根据已有阶段记录或用户指定的交接位置续接；没有记录时只询问影响续接的最小信息，不默认从头执行。

## 调用方式与共同约束

先利用当前环境的 Skill 目录定位下表中的依赖，只确认可用性，不预读全部规则。进入某一步时，通过环境支持的 Skill 调用能力加载对应 `SKILL.md` 并按其要求执行；没有专门调用工具时，读取该 Skill 指令及其指定资料后执行，并如实说明。不能只提到名称、给出建议或复述摘要就标记为已调用。

优先使用当前环境安装的版本；在仓库工作时可按目录定位，不能假设独立安装后相邻目录必然存在。依赖缺失时提前说明受影响阶段，可继续此前不依赖它的步骤；到缺失阶段暂停并指出缺少的 Skill，不静默跳过、不伪造执行，不默认联网安装。局部工具或资源缺失时按子 Skill 的恢复规则处理。

用户当前范围和已有明确授权贯穿流程。普通步骤完成后自动进入下一步，不机械地逐步请求批准；需要产品决定、人工 Review、实施授权或新会话时，保留子 Skill 的边界，说明具体待处理事项。用户只要求审查、探索或限定终点时遵循该范围，不将编排请求扩张成全部实施授权。正常的完整流程请求包含在指定目标项目内生成初版和常规审查修正，但不自动授权发布、外部真实写入或跨越人工 Review。

只读帮助不依赖业务 Skill 是否已安装。非简体中文产品、非桌面平台等不符合子 Skill 范围时，报告适用性缺口并与用户确定如何处理，不宣称该项通过。编排层不自行放宽子 Skill 的适用范围。

## 顺序与交接

| 阶段 | 执行能力 | 输入与交付 | 推进条件 |
| --- | --- | --- | --- |
| 1. 设计塑形 | `aw-design-shaping` | 原始需求 → 已确认的设计简报、必要图稿与待定项 | 由该 Skill 完成聚焦追问、竞品研究、探索方式选择与方向确认；用户未回答关键问题时等待 |
| 2. 生成初版 | 当前执行者的实现能力 | 当前简报 + 项目组件库 + DESIGN.md → 可交互初版及运行入口 | 在用户目标项目与授权范围内完成；这一步不是另一个名为“生成初版”的 Skill |
| 3. 信息简化 | `aw-ux-info-redundancy-audit` | 初版及目标 → 信息价值判断、精简决定和获准改动 | 先有审计依据，再在已有范围内修正并验证 |
| 4. 组件修正 | `aw-component-checker` 的审查模式 | 当前界面 → 组件语义、组合及内部用法检查 | 依据审查结论完成已授权修正；不进入组件 Reference 编辑模式 |
| 5. 流程补全 | `aw-flow-completeness-audit` | 当前实现与需求 → 流程缺口、产品提案、验证限制 | 报告后等待人工 Review；用户审阅并明确授权后，实施选定事项并复查 |
| 6. 独立任务走查 | 新会话中的 `aw-task-walkthrough` | 需求依据、可操作入口 → 用户选定任务的观察与证据 | 用户选择任务；报告后人工 Review，后续按明确要求讨论与修正 |
| 7. 文案收敛 | `aw-wording-reviewer` | 走查后当前界面 → 一致化文案及适用验证 | 按其字符串/实现授权边界完成本次范围，报告剩余事项 |

生成初版前按需定位目标工程、组件库和适用 DESIGN.md，已有信息直接沿用。如果缺少会影响实现的资源，提出最小选择：用户提供已有资源，或明确采用项目现有约定/创建所需设计基础。不默默另建组件库或调用额外 Skill。没有可写目标工程时，先完成能独立进行的塑形，到实施边界再明确缺口。前端模拟应标明，不把模拟成功写成真实后端能力已验证。

每个阶段使用当前实现和最新有效需求。审查报告完成与修复完成分别记录；未解决的阻断不能自动算作通过。用户明确选择延期或缩小范围时保留其决定及影响，继续独立部分，不声称原范围全部完成。没有发现问题时沿用子 Skill 的完成与 Review 规则，不为了产生改动而制造建议。

文案收敛保持在任务走查之后；必要的解释性重复按 Wording 的一致化规则判断，不因前序做过精简就禁用这些规则。后续变更影响范围、主路径或关键业务规则时，同步已有简报及受影响图稿，区分批准、实施和验证状态；不将尚未批准的建议写成新事实。

## 人工 Review 与继续

需要等待时，给出已完成内容、报告位置和本次需要用户回答的具体事项。完整性审查的报告交付后必须人工审阅再授权实施，不能用最初“全流程完成”的笼统授权替代。任务走查默认只报告问题；用户审阅后要求修复时，按选定问题修正并验证，再进入文案收敛。用户明确接受无问题结果或延期事项后，可以继续下一阶段，不强制产生修改。

收到回复只推进其实际确认的阶段和范围。`/help`、询问进度、阅读报告或时间经过不代表批准。已批准事项不反复询问；新的关键产品取舍单列，不阻断已获准且无依赖的部分。

## 独立走查的最小交接

参与过设计、实现或前置审查的会话不能冒充 Fresh Context。第一版默认准备一段可复制到新会话的启动说明，由用户启动；不自动创建会话、派发子代理或引入调度器。若用户另外明确要求代建或交接，且工具支持，则按该授权操作。

交接只带目标项目、运行入口与必要环境条件、角色/测试数据范围、需求来源、任务目标和已有用户选择，并要求执行 `aw-task-walkthrough` 后返回报告位置。没有选过任务就让该 Skill 提出候选，不由编排器代选。允许完整 PRD；无 PRD 时可以引用当前简报，但注明其中路径、图稿和理由仅辅助规划。不要附带设计聊天历史、前序审查报告、问题答案或标准点击路线。不要在新会话走查前加载整份流程记录来污染首次观察。

新会话交付后，用户可回到原编排会话提供报告位置继续；也可在新会话明确调用本编排器继续。此时读取相关报告和已有 Review 决定，定位到走查后的人工审阅/修正阶段，再做 Wording，不从 Shaping 重新开始。用户明确要求同会话走查时遵循子 Skill 的降级规则，标明非独立，不宣称满足 Fresh Context。

## 最小进度记录与完成

复用项目已有任务记录；确需跨会话交接且没有记录位置时，在目标项目的 `docs/design/<topic>/run.md` 保存薄记录：当前阶段、简报/入口/报告位置、已获授权与待定事项、阻塞和下一步。业务内容仍由简报与审计报告维护，不复制全文，不建复杂状态系统。没有可写项目时在会话给出可复制记录。独立走查的启动说明另行给出，不能把含前序发现的 run.md 作为它的预读材料。

阶段完成、用户批准或目标发生变化时更新相关记录。发生变更只回到受影响步骤，不无故重新执行整条流程。用户暂停就保存可续接信息并停止；请求结束于中间阶段时明确交付范围。

完整流程交付当前版本入口、最新简报和报告位置、实际完成阶段及尚未解决/未验证事项。只有约定阶段均执行、人工关口已处理、获准修正与适用验证完成，才能称为本次流程完成；文件生成、单项审查通过或等待用户均不是全链完成。
