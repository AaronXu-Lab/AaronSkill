# 设计塑形工作流

将 PRD、模糊想法、竞品或它们的组合，转成用户认可、可交给组件库与 DESIGN.md 约束下的初版生成任务的设计简报。本文是唯一执行工作流；[流程图](../docs/workflow.svg) 是面向人的可视化投影，专项参考只补充研究与表达规则。

## 1. 建立当前理解

读取用户提供的材料及与目标有关的项目现状。输入可以从问题开始，也可以从已有方案开始，不要求先补成 PRD。提炼目标用户、使用场景、期望结果、已知约束与本次范围；区分用户明确要求、观察事实、AI 推断与待定选择。已有材料能回答的内容不重复询问；文档写得完整也不意味着其中的假设都已确认。

已有项目只读与本次任务相关的页面、能力和设计约定。组件库与 DESIGN.md 可提供现实约束，但不要求在塑形阶段逐项选组件或完成视觉规格。矛盾影响主方案时指出具体冲突；可独立研究的部分继续。

在最开始的追问阶段，说明并询问本次探索方式：

- 已有功能优化，推荐沿用现有结构与组件，针对有依据的问题调整。
- 新功能或重新设计，推荐先探索任务与结构，再核对落地代价。

用户可以选择另一种方式或限定哪些部分可变；已有明确选择直接沿用。自由探索仍受业务事实、必要约束与用户范围限制。等待该选择期间可继续只读了解背景，不把沉默当作选择。

## 2. 按决策依赖追问

维护当前最重要的未决问题，先处理会改变目标、范围、主要任务、页面职责或关键规则的决定。一个问题依赖另一个未定答案时，留到下一轮；可独立决定的问题可以同轮提出。每轮以用户能轻松回答为尺度，不固定问题总数，也不一次倾倒所有可问的问题。

每个实质问题交代具体场景、不同选择的影响，以及有依据的推荐；证据不足时明确缺少什么，不编造推荐理由。允许用户自行回答、混合方案或纠正问题本身。提问用于共同形成方案，不以让用户填写模板为目的。

- AI 主动查找可获得的事实，不把资料检索转交用户；无法访问时说明缺口。
- 目标、范围、主路径和代价明显的关键取舍由用户决定。
- 局部组织和表达由 AI 先提出或画出，可随反馈修改；提案不标成用户已确认。
- 可以挑战既定假设，但须说明具体场景、冲突或代价，并提供可讨论的替代方向。用户理解取舍后作出的决定应被尊重。

用户改变目标或前置决定时，重新检查受影响的后续选择和图稿，标记哪些已失效；不沿着旧问题继续追问。已确认的独立决定保留。

## 3. 选择能解决当前问题的探索手段

追问、竞品研究、方案比较和可视化可以交替使用，没有固定先后，也不要求每次全部执行。

| 当前不确定性 | 适合的行动 |
| --- | --- |
| 谁遇到什么问题、成功意味着什么 | 具体场景、反例与聚焦追问 |
| 不同产品如何组织同类任务 | 按 [竞品研究](competitor-research.md) 体验与查证 |
| 同一目标存在实质不同的解决方式 | 给出少量有意义的方案，比较用户成本与约束 |
| 页面职责、区域关系、导航或步骤难以口述 | 按 [可视化对齐](visual-alignment.md) 展示线框图或低保真交互 |
| 某个规则会改变主结构 | 用业务例子或决策表明确规则 |
| 当前系统能否支持影响方向的能力 | 做聚焦的只读查证或隔离的可行性探查，区分事实与尚未验证 |

每次行动明确要解决的待定问题。一个明显可行的方向不必为了形式凑出三个方案；有真实分歧时也不只呈现 AI 偏好的方案。用户只提供竞品名称时先初步研究，再带着具体发现收窄问题，不要求用户预先说清每个参考的价值。

探索原型可使用本地、隔离的示例数据，不连接真实写入。交互演示不证明后端能力存在。需要账户、付费资源或外部写入时遵循已有授权；不能取得的材料记录限制，继续能独立完成的部分。

## 4. 共同形成并比较方案

将需求与实现方向分开：需求说明用户需要达到的结果或必须满足的约束；方案说明任务如何组织、在哪里操作、如何得到结果。避免把同一句需求换个标题当作方案。

从真实场景明确：主要业务对象、任务起点、页面或区域职责、主要操作顺序、可观察的完成结果，以及影响主路径的上下文保留和关键分支。只深入会改变当前方案的交互规则；例如批量操作允许部分成功可能改变结果页，须先讨论。其余异常状态和 corner cases 留待后续流程完整性审查，不在此穷举。

存在多个方向时，用关键需求对照方案，必要时用小表标记「满足 / 不满足 / 待验证」，附简短依据。方案看起来满足要求而用户仍不认可时，追问具体场景或遗漏的取舍；不能直接替用户新增一项强制需求。讨论偏好也可以保留为偏好。

选择或修改方向后，同步更新受影响的简报、图稿和决定。保留有意义的放弃理由，避免维护所有草案的完整历史。事实依据、用户确认、AI 建议和暂用假设应可辨认，不用精致图稿暗示方案已确认。

## 5. 收敛与确认

当以下内容足以供初版生成时，呈现与任务规模相称的方案摘要，请用户确认或纠正：

- 面向谁、解决什么、本次包含和不包含什么；
- 主要任务、页面职责、关键路径和完成结果；
- 会改变主方案的业务规则及重要取舍；
- 仍存在的假设、证据缺口与留待后续的问题。

不要求所有细节都已决定。关键未决问题会导致两种不同主方案时，先解决它或明确交付仍为草案；次要问题可保留为后续事项。用户对局部图稿的认可不自动视为对全部方案的确认。用户已经明确认可当前完整方向时直接沿用，无需重复审批。

如用户提前结束、只要求探索某一部分或暂时无法回答，保存当前进度与下一个需要的决定，标为「探索中」，不伪称塑形完成。没有真实用户回答时不能模拟同意。

## 6. 交付初版生成所需上下文

复用项目已有设计文档位置；没有约定时在目标项目的 `docs/design/<topic>/` 保存一份 `brief.md`，必要图稿放同目录。没有可写项目时先在会话交付完整简报，说明尚未落盘；不要把业务资料保存到本 Skill 仓库。

简报按需要包含以下信息，简单任务合并为短段落，不强填空章节：

- 目标、用户场景、成功结果及范围；
- 选定方向，任务路径与页面/区域职责；
- 影响初版的关键规则、已有设计约束及探索方式；
- 必要的线框图或可操作原型入口，并说明表达范围；
- 关键决定与理由，重要参考的来源及借鉴/不采用原因；
- 暂用假设、未验证能力和后续状态检查事项。

让接手的新会话无需阅读完整聊天就能继续。正文与图稿应指向同一当前方案；不强制另写 PRD、开发任务拆分、实现计划或多个相互重复的文档。

简报是可持续更新的当前设计依据。交付时注明适用版本或基线，将已确认的目标与业务规则、暂用假设、方案路径及取舍理由分开表达。后续审查或实施经用户批准改变范围、主路径或关键规则时，由处理该变更的阶段同步受影响的简报与图稿，简记新决定、依据及被替代内容；记录“已确认待实施 / 已实施”等实际状态，不能把批准当作实现完成。局部措辞与样式变化不要求重写整份简报。尚未批准的建议保留为提案，不覆盖当前决定；已有项目事实源优先，简报引用它，避免维护冲突副本。

后续任务走查可以把简报作为选择任务和规划覆盖的辅助参考，其中的路径、图稿和取舍理由不作为标准答案，也不能覆盖实际界面证据。

交付前检查主路径可解释、关键分歧已处理、来源与推断分明、图文一致、用户确认覆盖当前方向。可操作图稿检查用于讨论的关键交互；只读资料或静态图不能声称经过实际运行验证。

报告已确认内容、文件/图稿位置和剩余问题。下一阶段是结合组件库与 DESIGN.md 生成初版；本 Skill 不自动改正式业务代码。若同一用户请求已授权后续实施，交付塑形结果后按该授权继续，不制造新的重复确认。
