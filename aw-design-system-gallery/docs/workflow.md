# AW Design System Gallery 工作流

本文档是执行 `aw-design-system-gallery` 的文本事实源。`workflow.svg` 是与本文档同步的可视化投影；两者不一致时，以本文件为依据修订 SVG。

## 输入与产物

- 输入：设计系统中的组件、样式/Token、规则、模式或组合场景，以及已有 Gallery 或从零建立 Gallery 的请求。
- 产物：与各类设计系统事实源对齐的 Gallery；若获授权且确有必要，还包括组件 API 或其他源定义的调整；同时包含验证结果或明确的事实源缺口报告。

## 主要阶段

### 1. 确认范围和授权

读取目标仓库规则，确认 Gallery 范围、目标 section 类型、允许修改的事实源，以及可用的运行和验证入口。

若目标其实是产品页面、业务 fixture、营销页或调参面板，停止套用本技能的 Gallery 结构，改用该表面的本地规则。

### 2. 收集实现证据

定位并阅读：

- 组件实现、公开类型和导出；
- 样式、Token 与底层 primitive；
- 设计规范、lint/测试约束与模式文档；
- 代表性真实调用点；
- 已有 Gallery shell、成熟 section 和展示 helper；
- 类型检查、测试、构建和开发服务器命令。

不要从旧示例单独推断默认值或公开轴。

### 3. 分类 section 并审计事实源

先将目标分类为组件、样式/Token、规则、模式/组合场景或内部调试面。内部调试面不纳入面向使用者的 Gallery 信息架构；其余类型分别以公开 API、Token 定义与模式、规范约束、组合契约为事实源。

只有组件 section 执行 `references/component-api-design.md`：识别默认用例、视觉/内容/状态/行为轴、有效默认值、状态控制、事件、slot 与可访问性契约。

判断 API 是否存在实质缺口：如果 Gallery 必须虚构 prop、隐藏冲突默认值、依赖私有 wrapper 或同时改变多个不相关 props 才能解释一个轴，则为实质缺口。

- 无实质缺口：继续。
- 有实质缺口且已授权修改 API：先进行最小 API 重构，更新范围内调用点，再继续。
- 有实质缺口但未授权修改 API：停止该部分实现，交付具体缺口、影响和建议决策。仍可处理不受影响且能诚实展示的组件。

### 4. 选择 Gallery 模式

判断目标是否已有可维护的 Gallery 基础设施。

- 已有：沿用当地 shell、导航、helper、状态模式和视觉语言，只规范化目标 section。
- 没有或已不可运行：使用项目现有技术栈从零建立最小 Gallery 骨架，不默认引入文档站依赖。

从零骨架包含稳定 section、Caption、适合各类内容的展示舞台，以及项目已有主题和交互状态所需的最小环境。只有 section 数量带来查找成本时才添加分类、导航或搜索。

### 5. 建立展示模型

依据 `references/gallery-rules.md` 为不同 section 建立合适的展示模型：

1. 组件：`default` 完整基线、主要公开轴、必要状态和中性内容；
2. 样式/Token：语义分组、源值或别名、模式与可辨识的视觉样本；
3. 规则：正例、反例、理由、适用条件和边界；
4. 模式/组合场景：代表性任务、参与部分、关键状态和响应式行为。

比较时只改变目标轴，并依据组件自然尺寸选择横向或纵向布局。

### 6. 实现与同步

实现或整理 Gallery。Gallery 使用中性内容，不修改真实产品文案或业务数据。

只有 API 实际变化时，才同步公开导出、类型、测试和所有范围内调用点，并搜索废弃 prop 与旧 Caption。

### 7. 验证

运行目标仓库已有的类型检查、lint、测试和构建命令。启动 Gallery，按 section 类型与组件适用性检查：

- Caption、默认值和示例顺序；
- 主题、背景和 Token；
- Token/样式值、规则边界和组合场景是否可追溯到事实源；
- 常见视口与比较方向；
- 键盘、焦点、禁用、错误和交互状态；
- 浮层、滚动和 overflow；
- 从项目标准入口稳定运行。

验证失败时先修复，再重复最小相关验证；不要在失败状态下宣称完成。

### 8. 交付

报告修改的事实源或组件/API、Gallery 结构、调用点同步、验证结果和任何保留的债务。只交付请求范围，不顺手统一无关 section。

## 停止条件

- 目标不属于面向使用者的设计系统 Gallery。
- 缺少对应事实源，且无法可靠确认内容、默认值、模式或边界。
- API 存在会导致 Gallery 误导的实质缺口，但没有修改授权。
- 必需的仓库验证持续失败，无法在当前范围内修复。
- 继续需要新增依赖、扩大真实产品修改范围或作出破坏性 API 决策，而这些未获授权。

## 最终检查

最终产物必须让 Gallery 成为设计系统事实源的真实投影，而不是另一套会漂移的手写故事。文本、视觉顺序、交互行为、公开类型、Token 和规则应能互相验证。
