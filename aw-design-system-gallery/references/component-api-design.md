# 组件 API 设计约束

按入口路由仅读对应小节：设计轴命名和跨组件一致性读 §2；组件身份读 §5；公开边界读 §6。评估或实施 API 变更才补读 §1、§3、§4。目标框架与项目约定优先。

## 代码检查路由

目的是使组件在开发调用时满足一致标准；只调整 Gallery 文案或布局不自动触发完整代码审查。完整第 3 项覆盖以下适用内容，局部修改只读相关小节：

| 问题 | 细则 |
| --- | --- |
| 公开可调用属性、类型和值域是否清楚，API 是否表达稳定概念，组合属性是否归属实际职责所有者 | §1 公开契约及组合职责与属性归属 |
| 同语义命名、Gallery 到 API 映射、平台原生属性透传 | §2 平台保留能力与映射 |
| 默认值、受控／非受控状态、回调与无障碍语义 | §3 默认与状态及 §7 开发行为与健壮性 |
| 文档页面名与真实组件调用名、导出名、目录及路由的对应关系 | §5 组件身份与 Gallery 映射 |
| 父子组件依赖、公开边界、内化 | §6 公开子组件与内化及 §7 |
| 空数据、异常值、极端尺寸等健壮性 | §7；是否正式展示另由正式设计轴标准决定 |
| 实施代码变更后的类型、调用点和验证范围 | §4 修改边界 |

## 1. 公开契约

- 公开 API 应表达消费方理解的稳定概念；不要为了排出整齐 Gallery 而制造轴或参数。
- 几何、视觉、内容、状态和行为尽量正交；存在真实依赖时明确父子关系。
- 互斥模式使用目标语言和框架适合的类型结构，避免允许冲突组合的多个开关。
- 内容通过目标框架惯用的 slot、内容入口或组合机制表达；样式扩展使用项目支持的机制。

### 组合职责与属性归属

- 从实际渲染与配置消费位置确定职责所有者。组合组件管理自身的结构、区域显隐和组合关系；嵌入组件已有的内部配置与行为，原则上由嵌入组件管理，避免在父组件重复建模、另设默认值或形成两套规则。
- 父组件只有在组合后产生独立语义，或有依据需要统一配置入口时，才暴露对应属性；明确其与子组件配置的映射、默认值及优先级。不因实现中简单透传、当前 API 已存在或 Gallery 已有轴，就认定该属性应归父组件；也不机械禁止所有透传。
- 区分“整个区域是否存在”和“区域内部如何配置”。前者可属于父组件，后者追踪到实际子组件；不将区域显隐与内部布局、操作数量或样式揉成一个枚举。沿用项目命名约定，不强制所有组件采用同一显隐属性名或极性。
- 验收同时追踪公开类型、运行时默认、子组件调用、Gallery 默认／比较轴及 Usage／Composition，判断它们是否共同描述正确的职责边界。问题主要归第 3 项；展示侧的连带影响在同一问题说明，不重复编号。仅修改文案或隐藏轴不能算完成 API 职责修复；API 迁移按授权同步调用点并验证。

## 2. 平台保留能力与映射

- 先确认实际宿主、目标框架的平台保留属性和值域，再对照同项目相同 Gallery 设计语义的代码命名。按语义统一，不按字面字段批量改名；不同结构、业务、媒体分类不能仅因都叫 `type` 就归为同一轴。
- Gallery 名称与实现 API 不同时，比较语义、值域和转换，而非只看字面名称。
- 项目声明了映射配置时遵循；没有时仅记录当前组件的现场判断。可唯一确定的映射与真正歧义，按 [工作流的局部阻塞规则](../references/workflow.md#停止与局部阻塞) 处理，不因 Skill 示例修改 API。
- Gallery 展示模型保留设计值。默认值、属性轴、编辑控件、选项标签、Caption 与说明不得因为组件类型已改名而改用代码值；代码值只进入组件调用、类型检查和运行时分支。
- 在 Gallery 的渲染适配边界显式完成转换：可让 Gallery 状态持有设计值后转换为组件 props，也可让控件使用“设计 label + 代码 value”的成对选项。不要把存在映射的 Gallery 状态直接 spread 到组件，也不要依赖 `String(codeValue)` 自动生成用户可见文案。
- 代码 API 更新后，搜索旧值与新值在 Gallery 中的全部用途，分别核对默认编辑器、属性轴 Caption、页面描述、演示触发器和渲染调用。旧设计值仍可正确留在展示侧；新代码值只能留在适配侧。类型通过不能证明展示映射正确。
- 公开自定义参数的声明与实现读取顺序，可在不破坏类型继承、平台透传或运行时语义时尽量跟随 Gallery 的最终语义顺序。
- 组件 API、Gallery 轴与演示条件的区别，按 [正式展示与 Caption 规则](design-axes.md) 判断；不能为排版或填充 Caption 而新增组件参数。

当可选结构的缺省状态本身具有独立设计审阅价值时，Gallery 设计模型可以用 `none` 表达该结构未出现。`none` 是设计状态，不要求成为组件公开 API 的字面值；在 Gallery 到组件的渲染适配边界，可将其转换为省略属性、`undefined`、`false` 或对应的代码值。结构固定、没有缺省状态或缺少独立审阅价值时，应省略该轴，不为补齐值域而添加 `none`。

### 设计轴命名预检

- 在定义新增或改名轴的状态键、编辑控件、Caption 和文档前，逐轴核对「设计属性名 → 代码属性名」「设计值 → 代码值」、两侧默认值及项目依据。依据优先来自项目约定、已声明映射和同语义组件；相同名称也明确为直接对应。不要求额外建立配置文件或公开 Props 表。
- 属性名与属性值分开判断：值完全相同仍可能需要属性名映射。例如项目已约定设计 `type` → API `contentType`，即使两侧都用 `single` / `multiple`，编辑器和 Caption 也不能显示 `contentType`；项目已约定 `style` → `variant` 时同理。这些是有项目依据时的例子，不是对所有组件或项目的固定改名规则。
- 实施范围内的全部轴都做此预检，不能只核对刚被指出的一个轴。只改已有轴顺序或占位文案时不触发全页审查。证据能确定的映射直接实施；有实质歧义时按工作流局部处理，不通过擅改组件 API 消除展示问题。

### Gallery 到代码的命名

- 设计属性以已确认的 Gallery 最终名称、值域和语义为基准。代码名称仅为适配目标语言、框架原生能力或项目明确约定而映射，不另造一套设计概念。
- 在 JavaScript/TypeScript 中，组合值使用 lowerCamelCase：将表达组合关系的 `+`、`&` 转为词边界，保留各部分的顺序和数量；Gallery 继续使用便于设计阅读的原表达。

| Gallery 值 | JavaScript/TypeScript 值 |
| --- | --- |
| `icon+text` | `iconText` |
| `avatar+text` | `avatarText` |
| `title+description` | `titleDescription` |
| `+subtitle` | `withSubtitle` |
| `+description` | `withDescription` |
| `+icon&text` | `withIconText` |
| `+description&time` | `withDescriptionTime` |
| `+content` | `withContent` |
| `+footer` | `withFooter` |
| `+content&footer` | `withContentFooter` |
| `secondary+primary` | `secondaryPrimary` |
| `secondary+secondary+primary` | `secondarySecondaryPrimary` |

- 开头的 `+` 表达基于默认内容的追加时，代码值使用 `with` 前缀，后接 PascalCase 内容名，例如 `+subtitle` → `withSubtitle`、`+content&footer` → `withContentFooter`，保留原有累进渲染语义。没有前导 `+` 的组合仍使用普通 lowerCamelCase，例如 `icon+text` → `iconText`。若转换会造成同一值域内重名，或符号并非组合关系，先按语义消除歧义，不机械替换。
- 同一项目中相同 Gallery 设计语义使用统一代码名称；命名以该语义及项目已确认的跨组件契约为依据。不能仅因某组件没有平台冲突，就让相同内容组合一处叫 `type`、另一处叫 `contentType`。视觉 `style` 通常对应 `variant`，图标／文字内容组合的 Gallery `type` 通常对应 `contentType`；具体统一契约由目标项目确定，不把 Skill 示例扩展为跨项目机械改名。
- 平台原生能力不能被设计轴挪用。React `style` 保留样式对象，按钮／输入框原生 `type` 保留平台值域；设计语义通过统一自定义名称表达。宿主确有不同原生约束（如输入框原生 `size`）时，明确该约束及项目映射，不覆盖原生能力、不虚构透传。
- 项目内设计名 → 代码名、设计值 → 代码值的转换须显式、集中维护，复用同一语义转换入口；不要依赖各组件零散隐式转换。命名债务应在获授权的组件／Gallery 源头修正，不能靠 MCP 返回的逐组件例外掩盖；MCP 只反映真实契约。
- 状态轴可映射到框架惯用的 `checked`、组 `value` 等受控入口；内容仍通过独立 slot 或内容属性传入，避免为了名称一致而覆盖原生能力、吞掉内容或维护两套状态。
- 已授权实施 API 对齐时，在目标项目记录 Gallery → 最终代码契约的映射，同步类型、实现、Gallery 适配和实际调用；消费方迁移使用已实现并验证的最终契约。Skill 更新本身不代表已批准表中所有组件的 API 修改，也不授权发送消费方任务。

### 映射验收

- 对照同语义组件的公开属性名、类型别名、值域和默认行为；检查组件实现、库内调用、Gallery 渲染适配、编辑器、Caption 与说明同步，确认旧公开入口不再误用。
- 实际验证相关原生 `type`、`style` 等平台能力仍按契约工作；原生 `type` 不能收到内容组合值，设计值不能通过对象 spread 泄漏到宿主元素。
- 从 Gallery 侧选择每个设计值，确认默认预览与属性轴渲染到对应代码分支。
- 分别核对属性名和值：编辑控件及其可访问名称、轴标题、Caption、默认值字段、选项标签和属性说明均使用设计侧名称／值；即使设计值与代码值相同，也检查代码属性名未泄漏。API 用法或集成代码中明确说明代码属性不算泄漏。
- 检查组件调用中没有误传带 `+`、`&` 等设计符号的值；若组件契约本身明确使用这些符号，以真实 API 为准并记录该项目例外。
- 对可编辑默认值验证往返：切换值后展示标签仍是设计名称，重置后恢复设计默认值，组件收到对应代码值。

## 3. 默认与状态

- 默认值按 [工作流中的证据优先级](../references/workflow.md#2-按问题取证) 确定。
- 检查范围内逐项对照设计属性默认值与组件实际运行时缺省行为，并按设计名／值到代码名／值的映射比较语义，而非只比较字符串。追踪参数缺省、内部回退、继承的 primitive、受控／非受控状态、复合子部件和条件适用性；无默认、必填内容或仅由调用方提供的示例值须明确区分，不能臆造默认值。
- 对照公开类型／注释、项目规范属性表、Gallery 初始值及 Reset、预览传参和实际呈现，以及项目提供的生成数据或 MCP 默认信息。能由源码和有效测试确定的直接记录证据；有疑点或项目／用户要求时按验证规则复核运行结果。未覆盖或未验证项不得判为通过。
- 标为组件 `default` 的设计属性和展示应对应实际缺省；存在差异时记录属性、两侧取值、映射与证据，并按授权修正。Gallery 推荐组合可以不同，但须明确标为示例或推荐并展示所选值，不能冒充组件默认；项目或用户明确选择优先，公共行为有歧义时不要擅自修改 API 来消除差异。
- 受控/非受控状态、事件和可访问性遵循目标框架惯例，不维护竞争状态或泄漏不稳定内部结构。
- 状态应暴露正确的平台语义；可见错误、忙碌、选中、展开或禁用状态不能只依赖颜色。

## 4. 修改边界

按 [工作流](../references/workflow.md#1-确定范围与模式) 核对修改授权；Gallery 审阅可报告 API 债务。实施 API 修改时，检查公开导出、类型、实现、受影响调用点与测试，并验证平台保留能力仍能正常透传。

## 5. 组件身份与 Gallery 映射

以页面显示的组件名称为组件身份的事实源。检查时同时列出显示名称、公开组件类名／导出名、源码目录及 Gallery 路由：例如 `Stat Card` 对应 `StatCard`、`StatCard/` 和 `/components/stat-card`。组件类名／导出名与目录使用 PascalCase，路由使用 kebab-case；保留名称中的缩写（如 `WF`、`DS`、`OTP`）。同时检查样式文件名、显式 displayName、注册表、搜索／导航、文档链接和多语言映射，不能只确认页面标题或类型检查通过。

名称不一致时，在只读检查中列出差异及具体修改建议；已有改名授权时同步组件、目录、路由和本次范围内的引用，再验证新地址实际显示对应名称，不能以旧别名掩盖未完成的改名。复合组件子项（如 `Tabs.Item`）、共用实现文件、内部别名和组合示例先识别其真实契约，按用户授权范围处理；不因缺少独立目录便强行拆组件，也不把目录父分组名称当作组件名称。改名涉及消费者时遵循项目的跨项目迁移规则。

### 页面名与组件调用名验收

第 3 项检查须从文档标题／页面 ID 出发，沿 Gallery 实际调用核对公开导出及实现，明确记录“文档名／页面 ID → 真实调用名”的对应关系；不以目录名、去空格后猜测的名字或 MCP 返回名代替源码证据。

- 常规空格、大小写和 kebab-case／PascalCase 转换视为同名；保留缩写。子组件记录完整调用路径（如 `Tab Item` → `Tabs.Item`），不要求另造同名顶层导出。
- 页面名与导出名实质不同时，核对是否有用户决策或项目契约支持，并在项目文档或已有身份映射中明确实际调用名。已有明确依据的映射可保留；缺少依据、文档误导调用或引用未同步时，按第 3 项报告差异、位置及建议，不能靠新加别名消除报告，也不因本检查擅改公开 API。
- Gallery 内部组件核对其真实内部入口，并说明不从组件库导出；不要误判为公开导出缺失。已确认映射须在导航、搜索、示例／小窗口预览及 MCP（项目存在时）中指向同一身份；机器消费者不得因按页面 ID 猜导出名而丢失真实属性。

组件身份命名与属性映射分开检查；本次还涉及设计轴命名或 API 值时，再读 [命名预检与映射](#2-平台保留能力与映射)。

## 6. 公开子组件与内化

- 先区分公开复用组件与父组件的内部实现部件。仅服务于父组件、没有独立消费契约的子组件，经用户确认后应内化到父组件，不再公开导出；不能仅因名称像子组件、调用次数少或当前无调用就自动内化。调用审查包含父组件和其他组件内部使用，并区分独立业务使用、组合调用和纯展示调用；证据不足时先给建议并请求确认。
- “不展示”仅移除独立 Gallery 入口；“内化、不导出”还须合入父组件的实现或 API，取消包入口及公开子路径中的组件与专用类型导出，迁移获授权范围内的调用、测试与文档。不得仅隐藏入口、改成公开命名空间别名，或让调用方绕过包入口引用私有实现。跨项目迁移仍须遵守原有授权边界。
- 内化后在父组件中验证原有行为、无障碍语义和必要样式，并确认旧导出不可用；不再为内部部件保留独立组件页面。仍保留公开契约的子组件按 [父子展示规则](gallery-examples.md#父子组件展示) 呈现。

## 7. 开发行为与健壮性

检查 Gallery 事件示例时按 [交互归属](gallery-examples.md#交互归属) 区分组件内在行为与调用方效果；不能因使用无副作用回调而免验组件自身的状态与事件契约。

核对公开可调用属性的类型、值域、默认值及实现读取一致，包括未进入 Gallery 正式矩阵的能力。回调与事件应按契约触发并传递实际值；受控／非受控状态按框架惯例管理，避免竞争状态、重复事件或为展示效果吞掉回调。

区分属性依赖与组件依赖：前者核对条件、失效行为和值保留，并与 [Gallery 依赖展示](property-model.md#属性依赖与失效展示) 对照；后者核对 Root、Provider、父子结构或上下文的真实要求和公共调用方式，不用视觉 wrapper 掩盖缺少运行前提。公开边界调整仍须遵循内化和迁移授权。

根据实际契约验证空数据、未知或无效输入、内容扩张、极端有效尺寸、overflow 等相关案例，确认回退、布局和交互可理解；不凭空要求组件支持契约之外的输入。健壮性验证用测试或临时验证，能接受某输入本身不能证明需要正式 Gallery 场景。

验收采用与风险相称的类型检查、真实调用或行为测试；涉及状态时观察更新与回调，涉及原生属性时验证透传，涉及父子关系时验证合法组合及必要的错误反馈，涉及无障碍时核对语义、键盘与焦点。保留证据，未实际验证的能力不判通过。
