# Components 章节标准

按 Components 入口选中的章节读取；页面顺序与出现条件由 [页面结构](gallery-page.md#组件页面内容结构) 维护。说明文案复用目标项目的 MDX、语言和共享内容结构，不另造逐组件格式。

## Anatomy

Anatomy 不是必须项；仅在组件自身拥有值得说明的可视构成时展示。不适用的情况较少也不能将其视为必有章节。先区分组件自身拥有的可视部位与调用方或组合组件提供的内容，再按可见 UI 层级标注部位，标注与实际示例一一对应，用直白语言说明每部分的功能、作用对象及必要关系；不把 DOM 树、内部文件名或技术 wrapper 直接当作 UI 构成。

Container 类组件通常负责排列、包裹、裁剪或行为管理，没有自身独立实体，因此默认省略 Anatomy；调用方内容、复用子组件和辅助溢出机制不自动构成拆解理由。只有确有独立且值得解释的自身可视部位时才保留判断空间，不按分类名、DOM 或示例里可见的子控件机械判断。

仅管理展开／收起、状态或交互行为的组件，不因接收 header／children、影响外部可视内容或管理 trigger／panel，就被要求新增 Anatomy；DOM wrapper、上下文和行为机制不算可视部位。以组件真实实现与视觉归属判断，不按组件类别机械省略；若组件确实拥有值得解释的可视部位，仍应展示。是否需要说明组合或上下文依赖，由 Composition 或代码契约独立判断。

同一位置、同一职责、随状态互斥切换的形态归为一个稳定部位，名称按职责抽象；不按图形名或渲染分支拆成多行。形态差异在同一部位说明中解释，并由设计属性／状态表达；同时存在且承担不同职责的自身部位仍可分别标注。

Element 表达部件身份，使用简短、明确的名词或名词短语，按稳定职责命名；避免重复组件上下文，同类部件在项目内尽量使用一致名称；避免用 and／or／斜杠罗列形态或分支，删除不增加辨识度的修饰词，把形态差异和行为放入 Description。名称简洁不意味着合并同时存在且职责不同的真正部位；先判断职责，再选能准确概括的短名。

Description 表达部件职责，回答“它负责什么、作用于什么对象”。显隐条件、属性取值及配置方式放入属性说明，不能替代职责说明；可选性由 Required 等既有字段表达。名称和说明分别承担身份与职责，不把配置条件当作部件用途。

验收适用性、部位归属、状态抽象与名称，再核对部位位置与名称一致、主要部位无遗漏、层级可辨、说明能脱离源码理解；没有独立解释价值时省略，不为填满章节硬拆部位。

## Interactive Demo

可选。先判断是否存在需要实际交互才能理解、值得独立体验的组件行为；Playground 或 Properties 已充分表达时不重复。浮层、流程或动态反馈需要独立触发时可保留本章节，不因终态截图相同否定价值。

仅保留解释当前组件核心 UX 所必需的演示；支持或复用某子组件、存在集成用例，不构成把子组件专属行为或综合流程塞进本章节的理由。先说明每个演示回答哪个当前组件问题，将其他组件的专属演示归回其所有者；可保留有明确必要性的最小上下文，不绝对禁止组合。组合关系按 Composition 判断，完整任务／集成案例归项目独立 Example 或相应 Scenario，不借 Demo 扩大当前组件职责。

演示前按 [交互归属](gallery-examples.md#交互归属) 确认行为归属，不因回调存在而追加调用方业务效果。使用项目共享的演示触发器、舞台、状态反馈与重置方式；默认体验继承 Playground 当前设置。触发器清楚说明动作，演示调用真实组件，支持其契约内的打开／触发、状态反馈、关闭或完成、再次体验；键盘、焦点和可访问名称与实际行为一致。不把触发按钮本身伪装成设计属性，也不为每个组件另造演示框架。

验收先逐例核对核心 UX 归属与最小上下文，再检查首次与重复触发、关闭／完成后的恢复、设置变更和重置，以及鼠标与键盘路径。只比较某一属性的触发器留在该 Properties 轴内；纯健壮性案例留给测试或临时验证。

## Properties

仅展示 [正式设计轴](design-axes.md)，与 Playground 的属性、值、相对顺序及适用条件对应。两处共用定义和当前设置；编辑器专用内容项可按约定过滤，不为追求数量相等补造比较轴。

按 [实例数量](gallery-examples.md#实例数量) 核对每个 value 默认单实例及组合例外。每个比较实例只覆写当前逻辑轴，其他属性继承 Playground；不能为制造差异偷偷覆写父轴前提。比较差异不明显时不为该轴添加容器、背景或限高舞台，按 [设计轴](design-axes.md) 中“差异不明显”一段 处理。顺序变化读 [属性排序](property-model.md#轴排序)，适用条件变化读 [依赖与验收](property-model.md#属性依赖与失效展示)，宽度、对齐与排列变化读 [展示宽度与排列](gallery-examples.md#展示宽度与排列)，呈现变化读 [比较示例](gallery-examples.md#可比较示例)。

验收修改 Playground 的非目标属性后各比较实例同步更新、目标轴保留声明值；依赖失效、恢复与 Reset 按同一模型工作。Caption 使用设计侧名称与真实值。

## Usage

普通 Components 页面必有；例外按页面结构。复用当地 MDX 格式，从 UI/UX 角度说明何时使用、解决什么用户问题，以及内容、状态和交互形式如何选择；容易混淆时解释与相邻组件的选择依据。不只复述外观，不用泛泛的“展示内容”代替组件针对性说明。

### UI/UX 与开发接入边界

逐条检查 Usage 实际回答的是设计选择与用户体验，还是具体代码接入。参数传递、API 配置、属性推断与优先级、事件接线、受控／非受控状态管理、导入和代码调用等开发使用方式，归相应 API／开发契约文档，不放在组件 Usage；不能把从 Best Practices 移出的开发契约直接搬到 Usage 当作修复。标题写成“接入契约”“使用方式”或其他名称，不改变正文的职责归属。

例如“图标配合文字帮助识别对象类别”是在说明 UI/UX 选择，可保留；“必须显式传入 contentType，仅传入 icon 不会启用图标形式”是在说明参数与渲染契约，应迁出。提及属性或取值名称本身不构成违规：解释 `indeterminate` 表示组内仅部分选中、帮助用户理解选择范围，仍属体验说明；要求设置该属性的调用步骤属于开发接入。

验收时核对每条内容的目的、所属章节及译文；将开发接入说明记为第 7 项 Usage 问题，不新增报告列。只读审查记录位置、原因和迁移建议；获实施授权后迁到项目已有开发契约载体，并同步正文与译文，不为保留此类内容新建组件页面章节。


### 术语与使用说明

文档提及状态、属性或取值时，与当前公开 API 及 Properties 中的名称保持一致；代码标识用行内代码，不用未解释的别称替代。设计值与代码值的映射归开发契约，Usage 使用设计侧名称解释体验含义；可访问性或其他标准中的术语用于相应上下文，不直接充当组件配置值。

用法说明尽量使用直白语言解释含义及适用场景。不常见术语首次出现时，说明它表示什么、何时使用；抽象描述仍有歧义时，补充一个最小例子。说明应让读者能判断如何使用，而不只复述术语。例如用「`indeterminate` 表示一组选项中只有部分被选中」解释状态，避免只写「mixed 状态汇总集合」。不要求每个普通词都附定义，也不把说明扩写成 API 表。

验收正文、Properties、示例和译文中的术语一致，含义及使用条件清楚；发现不一致时同步相关事实源与译文，不仅替换当前页面的文字。

### 相似组件的场景比较

相似组件的选择比较保留在 Usage 中，并遵循：

- 同一场景或比较维度的候选组件合并为一个条目，不按候选组件逐项拆开。
- 小标题点明具体场景或比较维度，例如「选择与功能开关」，不用「相似组件的选择」等泛标题。同一组件涉及不同场景时，可以分别组织比较条目。
- 比较包含当前组件自身，说明每个候选组件分别适用于什么情况；组件自身的其他用法仍由各页单独说明。
- 所有参与比较的组件名均使用 Link，包括当前组件自身，兼顾跳转与链接颜色的显著标识；遵循目标项目的语言路由规则。
- 同一组比较在所有参与组件的页面中保持一致，正文与译文集中维护并复用。仅同步已确定的比较组，不扩展为全站关联普查。

例如 Checkbox、Radio、Switch 共用「选择与功能开关」条目，分别说明独立选择或明确同意、组内单选、功能启停；三个组件名均为链接。具体比较组及实现留在目标项目，不在 Skill 中维护组件清单。

验收格式与实际渲染、事实与组件能力一致、读者能据此判断适用场景。已有代码片段也按上述职责边界判断，具体 API 调用与接入步骤迁到开发契约，不能仅因代码正确就保留在 Usage。

## Composition

需要说明与关联组件组合时出现，覆盖常见且成立的组合即可。每个示例交代组合目的、各组件职责及必要依赖；不穷举组合，不把业务叙事当作通用组件契约。

Composition 解释组件之间的组合关系：与哪些组件搭配、各自负责什么，以及组合时的必要约束。围绕具体任务展开的完整流程、业务状态和操作步骤属于 Example，应归项目承载独立示例的文章类型；不因用了多个组件就留在 Composition，也不因出现具体任务名就机械删除简短的组合说明。

同一完整案例保留明确的维护位置。已有独立 Example 时，组件页不重复维护案例正文，仅保留理解组合关系所需的简短说明，并通过 [关联文章](gallery-page.md#关联文章) 提供入口。检查同节全部内容的实际职责，不只移除被点名的小节。迁移时检查译文、锚点及依赖案例正文的机器消费者，将必要契约移到正确事实源；不能仅删标题或留下依赖旧正文的悬空引用。

按 [父子展示](gallery-examples.md#父子组件展示) 核对子项默认值、组合外壳和独立矩阵。验收组合真实可运行、状态与交互可理解，父级示例不替代子级设计轴。

## Best Practices

Best Practices 从 UX 角度说明组件如何帮助用户理解信息、完成任务及避免误操作，覆盖选择语义、反馈、可发现性、无障碍体验等。属性优先级、状态来源、受控／非受控模式、参数传递及内部实现等开发契约不放在此节，归入相应 API／开发契约文档；不能仅因提到某个属性名就认定为开发建议，应按建议实际解决的是用户体验还是代码接入问题判断。

有具体建议时出现。每条建议说明可执行的做法与适用条件，必要时用正确／错误示例帮助理解；与当前组件能力、无障碍语义和项目设计约定一致。避免只有“保持简洁”“合理使用”等无法落实的口号。

验收建议可理解、可执行且有事实依据，与 Usage、Properties、代码契约无冲突；不重复堆放其他章节已有内容。
