# 正式设计轴与场景

新增场景、增删轴或改变 Caption 表达的属性／状态时读取；只调整已有顺序或占位内容无需重选。

只纳入能帮助理解组件视觉、内容结构、布局、动画行为或关键交互状态的公开设计轴，包括在当前组件中有独立审阅价值的几何、布局、视觉、内容构成、动画与状态。

公开属性控制可感知、可比较的动画或过渡行为时，可以成为正式设计轴。例如 `animated` 控制动画启用与关闭，形成动态过渡与即时切换的差异，应纳入正式比较；不能因为起止状态或静态截图相同，就将其判为纯实现机制。通过实际触发过程判断其设计结果，不按属性名称或是否涉及动画一概纳入或排除。

排除仅涉及实现细节、内部调度或没有独立设计审阅价值的机制，以及不形成可比较设计差异的行为、事件回调、纯数据载荷、测试或 debug 属性、内部状态、仅无障碍文案和没有独立审阅价值的底层子组件属性。组件 API 可以继续保留这些能力；公开或可配置本身不构成入选依据，仍按可比较的设计结果判断。

区分“组件调用所需数据”与“值得矩阵比较的设计属性”。数据可以驱动示例，但不必成为轴或出现在 Caption；组件 API、Gallery 展示轴与调试 props 不要求完全相同。项目已有明确契约或映射时以项目证据为准。按 [局部阻塞规则](workflow.md#停止与局部阻塞) 区分可确定的展示纠正与会实质改变结果的语义歧义；不能擅自改组件契约。

## 共享禁用态与设计轴

校验 `disabled`（或项目中的 `disable`）是否应列为设计属性前，先核对项目约定、共享 Disable 文档及现有实现；必要时查提交记录确认既有取舍。不能仅因组件公开了该属性，或禁用后外观发生变化，就要求新增设计轴。

采用项目统一默认禁用样式的组件，禁用属于共享运行时行为，由 Disable 或等价章节集中说明与展示；不在逐组件的 Playground、Properties、设计属性表或 Caption 中重复列为设计轴。缺少该轴不构成缺陷；已有重复控制与比较按审查或实施授权建议移除或移除。若项目尚无集中入口，先记录共享说明的缺口，不据此要求每个组件重复新增禁用轴。

保留组件真实的原生／primitive `disabled` API、必要的样式接入、交互阻断和禁用反馈抑制。统一处理指共享视觉规则、token 与展示职责，不要求由全局选择器接管所有实现，也不能据此把组件必要的禁用 CSS 或 API 判为多余实现。组件自身的结构依赖、失效配置和原因提示继续按 [属性依赖与失效展示](property-model.md#属性依赖与失效展示) 保留，不能与普通禁用设计轴混为一谈。

只有项目契约或实际证据表明禁用具有超出统一默认样式的组件专属结构、内容或关键交互差异，且值得独立设计审阅时，才评估是否保留该轴；记录具体差异与依据，不凭“可点击／不可点击”或统一淡化效果建立例外。运行时禁用行为仍按代码契约验证，不因未进入设计矩阵而免验。

## 其他正式场景边界

正式 Gallery 聚焦默认示例和有设计审阅价值的真实属性轴／状态对比。窄容器、限高滚动、溢出、异常输入、未知值回退或空数据等若仅用于验证健壮性，不默认添加为正式面板、独立场景区或现有面板中的额外示例。需要验证时使用测试或临时验证；审查范围内已有的纯验证展示应移除，不能只取消 Caption 后继续保留，也不能改名为“场景”或“边界”绕过筛选。

边界场景只有在用户明确要求展示，或有证据表明它属于当前组件的正式设计契约时，才按其具体范围纳入，不由一个例外扩展出整套测试矩阵。组件接受某种输入、存在 fallback 分支或能够滚动，本身不能证明对应案例具有正式设计含义。按展示目的和契约判断，不按名称一律排除 Empty State、错误、加载等有明确设计含义的正式组件状态。

例如，代码组件的窄容器、限高滚动、未知语言和空内容若只是检查布局或回退是否健壮，应留给测试或临时验证；它们不会因为公开 API 能接收这些值而自动成为 Gallery 对比。具有正式空态布局、提示和操作契约的 Empty State，则仍可展示其设计状态。若用户只要求展示某一窄容器行为，或滚动本身就是当前组件需审阅的正式契约，仅覆盖该要求，不追加其他边界案例。

Caption 只列真实公开 API 的属性轴与组件状态。`container`、stage width、演示容器尺寸、布局 wrapper、viewport、触发方式等若只用于建立演示条件，不是组件属性，不得出现在 Caption 中，也不得用貌似 prop 的写法包装。先判断示例是否符合正式展示标准，再决定说明方式；仅对已纳入展示且需要解释的条件使用页面描述或场景说明，说明位置本身不构成保留场景的理由。

比较应让目标差异清楚：同组示例只改变一个逻辑轴，保持值的声明与阅读顺序，并尽量固定与该轴无关的内容、环境和尺寸。项目可以用一组、多个场景或交互控制表达同一轴；不强制固定呈现形式。

差异不明显不是给 Properties 添加专用舞台的理由。比较实例沿用 Playground 当前的默认展示；不得仅因某个轴的值差异难以分辨——例如选中填充与默认背景同色，或冻结表头只在滚动后才可见——就为该轴额外加入容器、Panel、限高或预滚动视口、凹陷／有色背景、增加行数等专用舞台。先判断该轴：

- 属性是正式设计轴，但差异要靠交互、滚动或特定背景才显现：保留轴和默认舞台，由 Playground、Interactive Demo 或项目已有的背景切换工具体验；见 [可比较示例](gallery-examples.md#可比较示例) 中“必须通过交互才能辨别”的条目。
- 差异实质不存在、该轴没有设计审阅价值：按本文的正式展示筛选处理，而不是靠加舞台让它“看起来有差异”。
- 用户明确要求，或项目契约规定了该轴的专属舞台：按该要求或契约，范围仅限被指定的轴。

审计时，仅因比较差异不够明显而提出的“需要加容器／背景／限高”不是缺陷，不分配问题编号；确需运行证据的差异记为观察或待验。
