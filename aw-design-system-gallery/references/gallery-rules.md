# Gallery 审阅规则

本文件集中维护 Gallery 的详细判断标准。目标项目约定优先；以下规则不规定框架、文件格式或展示组件名称。

## 1. 先理解当地展示模型

- 读取适用的仓库规则、设计文档与 Gallery 约定，使用项目自己的展示单元、标签、比较容器和分类术语。
- 优先复用项目已有的内容、Caption、边界提示、Token、交互状态与验证方式。
- 项目声明了顺序表或属性映射表时，按其实际路径和格式读取；没有声明时不猜测隐藏配置。

## 2. 选择设计审阅轴

只纳入能帮助理解组件视觉、内容结构、布局或关键交互状态的公开设计轴，包括在当前组件中有独立审阅价值的几何、布局、视觉、内容构成与状态。

排除纯实现机制、只改善使用体验却不形成可比较设计变体的行为（例如过渡或动画机制）、事件回调、纯数据载荷、测试或 debug 属性、内部状态、仅无障碍文案，以及没有独立审阅价值的底层子组件属性。组件 API 可以继续保留这些能力；若某项确实形成需要比较的视觉、内容结构、布局或关键交互状态，再按其设计结果纳入。

区分“组件调用所需数据”与“值得矩阵比较的设计属性”。数据可以驱动示例，但不必成为轴或出现在 Caption；组件 API、Gallery 展示轴与调试 props 不要求完全相同。项目已有明确契约或映射时以项目证据为准，不一致或含糊时先询问用户，不能擅自改组件契约。

Caption 只列真实公开 API 的属性轴与组件状态。`container`、stage width、演示容器尺寸、布局 wrapper、viewport、触发方式等若只用于建立演示条件，不是组件属性，不得出现在 Caption 中，也不得用貌似 prop 的写法包装。若窄容器、固定舞台、溢出、响应式或特定触发情境对理解组件很重要，保留对应的视觉覆盖，并在 Panel description 或场景说明中写清条件与目的；不得通过删除必要场景来掩盖伪属性。

比较应让目标差异清楚：同组示例只改变一个逻辑轴，保持值的声明与阅读顺序，并尽量固定与该轴无关的内容、环境和尺寸。项目可以用一组、多个场景或交互控制表达同一轴；不强制固定呈现形式。

## 3. 决定轴顺序

1. 列出当前范围内的全部设计审阅轴。
2. 标出父轴与仅在父轴特定值下才有意义的子轴，将依赖组连续排列。
3. 对剩余轴使用可调整的兜底：几何/布局 → 主视觉 → 内容/槽位 → 状态 → 行为。
4. 让组件自身语义、用户决策或项目契约覆盖兜底；不要建立跨项目的固定字段优先级。

非约束示例：`surfaceMode → surfaceTone → surfaceHover`、`trailingSlot → trailingInteraction`、`sortable → sortDirection`、`contentMode → contentDetail`、`layoutMode → layoutPreset`。这些名称仅说明依赖形态，不是推荐 API。

如果项目使用 default 元数据与分轴展示，default Caption（存在时）的轴顺序必须按依赖关系组织，并与后续展示轴顺序逐项一致，而不只是集合相同。不要在 Skill 中维护具体项目的组件顺序表或属性清单。项目没有 default 或 Caption 概念时，不为满足 Skill 而新增。

组件没有适合矩阵展示的设计轴时，仍保留一个有意义的 default 示例和 Gallery 自己的 line-light 舞台边框，但省略 default Caption 整行，不渲染空 Caption。没有展示轴不自动意味着组件属于 Temporary；分类应依据目标项目的独立标准判断。

## 4. 核对 Gallery 名称与实现 API

- Gallery 名称服务于设计审阅，实现名称服务于目标框架和代码契约；二者可以不同。
- 检查目标框架的平台保留属性、组件公开 API、slot 或内容入口，以及样式扩展机制，不能仅凭常见名称推断冲突。
- 项目有映射配置时遵循；没有时只为当前组件记录现场判断。映射缺失、含糊或与实现不一致时，先向用户确认，不自动修改组件契约。
- 可复用关系应持久化在目标项目，而不是 Skill。写回任何项目配置前确认任务授权；未授权时只报告建议。

## 5. 构造可比较示例

- 优先使用目标 Gallery 的内容和 Caption 语法。没有约定时使用中性、清楚且不会被误认成产品默认值的内容。
- 内容、标签和示例数量应与所表达的比较关系对应；布尔或枚举值的展示顺序以项目约定和可理解性为准。
- 对没有自身背景或边界、需要辨认真实外框的组件，优先采用项目既有提示方式；没有约定时，可由 Gallery-only 虚线边界包裹。边界不得传入组件或改变组件自身实现与真实布局行为。
- 先估算比较容器的可用宽度与每个示例的固有宽度；只有能完整容纳所有示例时才使用单行。
- 单行无法容纳时，根据值数量、示例固有尺寸、比较目标和容器宽度，选择显式且均衡的网格或纵向排列。不要依赖 flex 自动换行，以免产生孤立末项、不稳定行数或误导性比较；也不要固化某一种网格或跨项目数值。
- 浮层、菜单、Popover、Tooltip 等需要审阅独立表面的组件，直接展示表面本身，避免用触发器把目标藏在交互之后。仅当触发方式是组件公开契约且构成当前审阅目标时，才把触发器纳入展示；触发器只是演示手段时放入场景说明，不写入 Caption。
- 对组件的最小/最大有效宽度、内容扩张、截断、换行、滚动和 overflow 建立明确的尺寸边界验证；不要用无限宽舞台掩盖问题，也不要把舞台宽度冒充组件尺寸属性。

## 6. 组织通用 Gallery 分类

- 通用设计系统 Gallery 按设计系统角色组织可复用内容，例如 Foundations、Composites，以及目标项目已有的等价通用分类。
- 不在通用 Gallery 中创建 Conversation、Commerce、Inbox 等产品领域分组。领域叙事、业务任务和产品专属组合留在产品 Gallery 或产品文档中。
- 组件跨产品复用时，以它在设计系统中的主要角色归类，不以当前产品中的使用位置归类。
- 调整分类只改变导航归属，不改变稳定的 Panel ID。迁移前后核对深链接、引用和置顶状态仍指向同一 Panel。

## 7. 检查清单

- 范围是否符合用户授权；扩展读取是否有明确理由？
- 是否使用目标项目的真实展示模型、术语和配置，而非 Skill 假设？
- 默认或推荐组合是否有可追踪证据；不确定处是否标记或询问？
- 是否只覆盖会产生设计审阅差异的公开轴，并排除无关技术字段？
- 是否区分调用数据、组件 API、Gallery 轴与调试 props，并避免把非设计能力写进 Caption？
- Caption 是否只含真实公开 API 轴和组件状态；场景条件是否改由 Panel description 或场景说明解释且保留必要视觉覆盖？
- 父轴与依赖子轴是否相邻；兜底层级是否仅用于无依赖轴？
- 若项目使用 default 元数据，它是否只列展示轴并与展示顺序逐项一致；无展示轴时是否省略整行 Caption 而保留 default 舞台？
- Gallery 名称与实现 API 的映射是否符合当前框架，且未占用平台保留属性？
- 示例是否隔离单一变量、保持声明顺序，并根据实际宽度采用稳定且均衡的显式布局？
- 示例是否中性、可比较、可访问，并遵循当地内容、line-light 舞台与边界提示约定？
- 浮层表面是否直接可见；尺寸边界、窄容器、溢出与响应式行为是否按组件需要覆盖？
- 通用 Gallery 是否保持领域中立；分类迁移是否保持 Panel ID、链接和置顶状态稳定？
- 语义排序、键盘路径、焦点可见性、可访问名称与状态表达是否完成复核？
- 组件行为、真实调用点、共享基础设施和项目配置是否只在授权范围内修改？
- 是否完成与风险相称的项目验证，并区分机器可检与语义评审？
