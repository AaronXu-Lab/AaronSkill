# Gallery 审阅规则

本文件维护详细展示规则。目标项目约定优先；执行模式与授权按 [工作流](../docs/workflow.md)。按入口路由读取相关章节，不默认通读。

## 1. 当地展示模型

使用目标项目自己的展示单元、标签、比较容器和分类术语，优先复用其内容、Caption、边界提示与 Token；不固定框架、展示组件名或配置格式。所需证据按 [工作流的取证范围](../docs/workflow.md#2-按问题取证) 获取。

## 2. 选择设计审阅轴

只纳入能帮助理解组件视觉、内容结构、布局或关键交互状态的公开设计轴，包括在当前组件中有独立审阅价值的几何、布局、视觉、内容构成与状态。

排除纯实现机制、只改善使用体验却不形成可比较设计变体的行为（例如过渡或动画机制）、事件回调、纯数据载荷、测试或 debug 属性、内部状态、仅无障碍文案，以及没有独立审阅价值的底层子组件属性。组件 API 可以继续保留这些能力；若某项确实形成需要比较的视觉、内容结构、布局或关键交互状态，再按其设计结果纳入。

区分“组件调用所需数据”与“值得矩阵比较的设计属性”。数据可以驱动示例，但不必成为轴或出现在 Caption；组件 API、Gallery 展示轴与调试 props 不要求完全相同。项目已有明确契约或映射时以项目证据为准。按第 4 节区分可确定的展示纠正与会实质改变结果的语义歧义；不能擅自改组件契约。

正式 Gallery 聚焦默认示例和有设计审阅价值的真实属性轴／状态对比。窄容器、限高滚动、溢出、异常输入、未知值回退或空数据等若仅用于验证健壮性，不默认添加为正式面板、独立场景区或现有面板中的额外示例。需要验证时使用测试或临时验证；审查范围内已有的纯验证展示应移除，不能只取消 Caption 后继续保留，也不能改名为“场景”或“边界”绕过筛选。

边界场景只有在用户明确要求展示，或有证据表明它属于当前组件的正式设计契约时，才按其具体范围纳入，不由一个例外扩展出整套测试矩阵。组件接受某种输入、存在 fallback 分支或能够滚动，本身不能证明对应案例具有正式设计含义。按展示目的和契约判断，不按名称一律排除 Empty State、错误、加载等有明确设计含义的正式组件状态。

例如，代码组件的窄容器、限高滚动、未知语言和空内容若只是检查布局或回退是否健壮，应留给测试或临时验证；它们不会因为公开 API 能接收这些值而自动成为 Gallery 对比。具有正式空态布局、提示和操作契约的 Empty State，则仍可展示其设计状态。若用户只要求展示某一窄容器行为，或滚动本身就是当前组件需审阅的正式契约，仅覆盖该要求，不追加其他边界案例。

Caption 只列真实公开 API 的属性轴与组件状态。`container`、stage width、演示容器尺寸、布局 wrapper、viewport、触发方式等若只用于建立演示条件，不是组件属性，不得出现在 Caption 中，也不得用貌似 prop 的写法包装。先判断示例是否符合正式展示标准，再决定说明方式；仅对已纳入展示且需要解释的条件使用 Panel description 或场景说明，说明位置本身不构成保留场景的理由。

比较应让目标差异清楚：同组示例只改变一个逻辑轴，保持值的声明与阅读顺序，并尽量固定与该轴无关的内容、环境和尺寸。项目可以用一组、多个场景或交互控制表达同一轴；不强制固定呈现形式。

## 3. 决定轴顺序

1. 列出当前范围内的全部设计审阅轴。
2. 标出父轴与仅在父轴特定值下才有意义的子轴，将依赖组连续排列。
3. 对剩余轴使用可调整的兜底：几何/布局 → 主视觉 → 内容/槽位 → 状态 → 行为。
4. 让组件自身语义、用户决策或项目契约覆盖兜底；不要建立跨项目的固定字段优先级。

非约束示例：`surfaceMode → surfaceTone → surfaceHover`、`trailingSlot → trailingInteraction`、`sortable → sortDirection`、`contentMode → contentDetail`、`layoutMode → layoutPreset`。这些名称仅说明依赖形态，不是推荐 API。

如果项目使用 default 元数据与分轴展示，default Caption（存在时）的轴顺序必须按依赖关系组织，并与后续展示轴顺序逐项一致，而不只是集合相同。不要在 Skill 中维护具体项目的组件顺序表或属性清单。项目没有 default 或 Caption 概念时，不为满足 Skill 而新增。

选择 default 的具体值或推荐组合时，再读取 [默认与状态](component-api-design.md#3-默认与状态)。仅调整已有轴顺序无需重选默认值。

组件没有适合矩阵展示的设计轴时，仍保留一个有意义的 default 示例和 Gallery 自己的 line-light 舞台边框，但省略 default Caption 整行，不渲染空 Caption。没有展示轴不自动意味着组件属于 Temporary；分类应依据目标项目的独立标准判断。

## 4. 核对 Gallery 名称与实现 API

Gallery 名称服务设计审阅，实现名称服务目标框架与代码契约，二者可以不同。核对名称时读取 [平台保留能力与映射](component-api-design.md#2-平台保留能力与映射)；判断默认值或状态时读取该文件第 3 节。只有评估或实施 API 变更时，才补读第 1、4 节；单纯调整 Gallery 顺序不触发 API 设计审查。

## 5. 决定真实占位范围提示

- 用“边界可辨识度 + 当前审阅的必要性”决定是否显示组件的真实占位范围：只有组件自身边界不明显，并且范围信息能帮助回答当前设计问题时才添加提示。该判断适用于任何组件类别，类别名称本身不构成触发条件。
- 优先复用目标项目既有的 Dashed Light / line-light 范围提示；没有当地约定时才选择等价的中性 fallback。
- 范围提示必须是 Gallery-only 的外部视觉辅助：不得传入组件、改变组件布局或真实布局行为，不得冒充公开 API，也不得出现在 Caption 中。边界已清晰或范围没有独立审阅价值时，不机械添加。
- 已有边界显示开关时，新增和修改的提示必须复用受开关控制的共享入口。直接使用基础 Dashed Light token 或硬编码虚线，即使开启时外观相同，只要关闭时仍可见，就不算完成接入。当前示例需要扩展支持时，在授权范围内补齐共享机制，不另建逐组件状态。
- 将提示与组件真实边框、边框 token 示例分开控制，不通过全局覆写基础边框 token 来关闭提示。提示出现在 Portal 或其他独立渲染容器时，确认其也能取得开关状态或受控样式。
- 通过项目现有开关验证本次涉及的提示：开启可见、关闭隐藏，切换不改变尺寸与布局，真实边框和 token 示例不受影响。保留项目的默认值及偏好记忆方式；验证结束按项目规范恢复预览，没有规范时还原验证前选择。
- 具体接入名称与实现方式以目标项目文档和代码为准，不在通用 Skill 中固定项目专属类名、属性名或变量名。项目没有边界开关时，沿用其现有展示约定，不自动引入新开关。

## 6. 构造可比较示例

- 优先使用目标 Gallery 的内容和 Caption 语法。没有约定时使用中性、清楚且不会被误认成产品默认值的内容。
- 在没有用户特别要求、项目事实源或当地约定覆盖时，Gallery 示例中的默认文本统一使用 `Text`，默认图标统一使用 `Placeholder`。只有存在明确语义或特别要求时，才使用其他文本或语义图标；该规则只约束 Gallery 示例的默认占位内容，不改变组件 API 或产品文案。
- 内容、标签和示例数量应与所表达的比较关系对应；布尔或枚举值的展示顺序以项目约定和可理解性为准。
- 若需要判断或调整真实占位范围提示，读取 [第 5 节](#5-决定真实占位范围提示)。
- 先估算比较容器的可用宽度与每个示例的固有宽度；只有能完整容纳所有示例时才使用单行。
- 单行无法容纳时，根据值数量、示例固有尺寸、比较目标和容器宽度，选择显式且均衡的网格或纵向排列。不要依赖 flex 自动换行，以免产生孤立末项、不稳定行数或误导性比较；也不要固化某一种网格或跨项目数值。
- 浮层、菜单、Popover、Tooltip 等需要审阅独立表面的组件，直接展示表面本身，避免用触发器把目标藏在交互之后。仅当触发方式是组件公开契约且构成当前审阅目标时，才把触发器纳入展示；触发器只是演示手段时放入场景说明，不写入 Caption。
- 不用无限宽舞台掩盖布局问题；尺寸与内容边界按 [第 9 节](#9-验证与恢复) 验证。

## 7. 展示复合组件与公开子组件

- 父组件 Panel 可以优先采用一个有代表性的组合，在同一整体示例中覆盖其公开子组件，以说明构成关系并减少重复展示相同的父级表面。代表性组合应服务于整体审阅，不要求枚举每个子组件的全部变体。
- 父级组合覆盖与子级属性矩阵承担不同任务：前者展示整体构成，后者隔离子组件自身的设计空间。父级组合中出现过某个子组件，不构成删除该子组件属性轴或变体的理由。
- 子组件 Panel 应移除不属于当前审阅目标的父级视觉外壳，包括父级背景、阴影、圆角、内边距及其他装饰性表面，使每个示例尽可能只呈现目标子组件。不要为了模拟完整父组件而重复引入会干扰比较的视觉环境。
- 子组件仍需保留所有具有独立设计审阅价值的公开属性轴。是否保留一个轴，应由它能否形成值得比较的视觉、内容结构、布局或关键交互差异决定，而不是由父组件是否已经展示过它决定。
- 必须依赖 Root、Provider 或等价上下文才能工作的 headless primitive，可以使用最小技术 wrapper 满足运行契约。wrapper 必须在视觉上不可见，不得引入父组件样式、改变目标子组件布局，或被误认为 Gallery 中正在审阅的表面。

## 8. 组织通用 Gallery 分类

- 通用设计系统 Gallery 按设计系统角色组织可复用内容，例如 Foundations、Composites，以及目标项目已有的等价通用分类。
- 不在通用 Gallery 中创建 Conversation、Commerce、Inbox 等产品领域分组。领域叙事、业务任务和产品专属组合留在产品 Gallery 或产品文档中。
- 组件跨产品复用时，以它在设计系统中的主要角色归类，不以当前产品中的使用位置归类。
- 调整分类只改变导航归属，不改变稳定的 Panel ID。迁移前后核对深链接、引用和置顶状态仍指向同一 Panel。

## 9. 验证与恢复

只核对本次涉及的规则和受影响行为；例如顺序改动对照第 3 节，范围提示开关对照第 5 节，父子展示对照第 7 节，分类迁移对照第 8 节。有结构化验证入口时可自动检查 default 与展示轴是否同序；依赖语义、正式展示目的和例外依据仍需基于实际结果评审，不以脆弱文本匹配代替。

- 主题视觉验证默认只运行 Light。组件和 Gallery 正确使用主题 color token，且无硬编码主题色、主题专属分支、已知主题缺陷或其他具体风险时，不重复运行 Dark；项目支持 Dark 本身不构成理由。上述条件不成立、用户明确要求或 Light/代码证据指向主题问题时，追加 Dark。
- 涉及交互或展示结构时，复核语义排序、键盘路径、焦点可见性、可访问名称与状态表达。
- 按组件与改动需要，用测试或临时验证检查最小/最大有效宽度、内容扩张、截断、换行、滚动、overflow 和响应式行为。是否正式展示由 [第 2 节](#2-选择设计审阅轴) 判断，验证完成后清理临时展示。
- 修改范围提示时，开关两态、Portal、真实边框与偏好恢复按第 5 节验收。其他临时预览选择也按项目规范恢复，无规范时还原验证前状态。

修复、重验、局部失败与交付状态按 [工作流](../docs/workflow.md#4-验证与交付) 处理。
