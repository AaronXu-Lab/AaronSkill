# 流程完整性审查工作流

本文是执行事实源，[流程图](../docs/workflow.svg) 是面向人的可视化概览。检查一个约定范围内的用户流程是否对必要步骤、分支、转换和结果给出了完整设计。以已实现界面为主要对象，兼容设计稿、原型及需求描述；不要求先生成完整 PRD。

## 1. 确定任务边界与证据

沿用用户已给出的目标、范围、角色和约束，从实际入口定位目标流程。明确预期完成结果，例如“接收者获得指定访问权限”，不能自动把“发送成功”视为同一结果。仅审查局部步骤时，记录它的上游条件和下游结果，不扩张为全产品审计。

优先查看实际界面、相关调用方、状态逻辑和适用需求，按问题追踪源码，不为局部审查遍历整个仓库。区分：

- 需求或已确认决定：证明行为应当怎样；保留适用角色、条件和例外。
- 运行观察：证明本次条件下实际发生了什么；记录入口、角色、数据和环境。
- 源码：证明实现声明了什么以及可能的调用路径；静态存在不等于用户可达或实际运行通过。
- 设计稿、截图、原型和描述：证明其明确表达的设计；未展示某状态不等于该状态不存在。

代码或现有界面不能反向证明需求已规定某行为。来源冲突时记录差异；没有 PRD 仍可识别内部矛盾和已证实的断点，涉及业务取舍则交付提案。

只执行已有授权允许的检查。需要提交、邀请、删除、支付或其他产生副作用的操作时，优先用已确认隔离的本地演示、测试账号或模拟条件；不能把审计授权视为对真实对象执行这些操作的授权。不可安全操作时采用静态证据并保留验证缺口。审计阶段不修改业务代码来制造场景或补全行为。

只有目标完全无法定位或关键范围无法区分时，询问最小必要信息。局部证据不足不阻塞其他独立分支。

## 2. 建立流程及交接关系

从真实入口按“前置条件 → 操作或系统事件 → 分支条件 → 新状态与可见反馈 → 后续动作或结束结果”追踪。保持对象、角色、选择、输入和权限等上下文的连续性；不把页面数量当成流程完整性的指标。

用项目现有表格或流程图记录；没有时按 [审计记录](audit-record.md) 建立可续接记录。每个分支说明：

- 谁在什么条件下进入，哪个动作或外部事件触发转换。
- 作用于哪个对象，产生哪些保存、发送、创建、权限变化等副作用。
- 用户能观察到什么，下一步由谁完成。
- 如何正常结束、取消或离开；适用时如何中断后重新进入或恢复。

跨角色或跨系统追踪到本次任务的真实结果。范围外环节只记录交接条件、接收方、预期结果、证据和依赖，不自动详细审查整个关联系统。依赖未核实会限制端到端结论，不能被当作当前范围已通过。

## 3. 按实际条件检查覆盖

检查正常路径是否缺必要步骤，再检查业务条件确实可能触发的其他路径。以下维度用于发现适用情况，不要求每个流程逐项生成状态：

| 触发条件 | 要判断的完整性问题 |
| --- | --- |
| 首次使用、无记录、无匹配结果 | 能否区分缺少前置条件与结果为空；有无适用的后续或结束方式 |
| 输入、业务校验、数量或容量限制 | 何时发现问题，如何修正，输入和选择是否保留 |
| 异步提交、后台处理、长时间等待 | 提交与最终成功是否区分；结果未知时如何确认，离开后如何找回进度 |
| 批量操作、多步写入、外部交接 | 部分成功如何呈现；已完成项与未完成项如何继续处理 |
| 网络中断、超时、会话过期 | 当前结果是否可判定；重新登录或重试是否丢失工作、重复产生副作用 |
| 多人编辑、重复操作、旧数据 | 冲突、重复提交及对象已经变化时如何处理 |
| 角色、归属、权限或资源变化 | 操作前后能力变化是否有交代；流程途中失去权限或对象被删除后如何结束 |
| 取消、返回、关闭、重新进入 | 中断的影响、已保存内容及恢复位置是否一致；取消界面与取消后台工作是否区分 |
| 不可逆动作或明确终态 | 后果是否在决策前明确；完成结果能否确认，无法恢复时是否给出合理解释或后续 |

按影响和发生条件选择分支，不做所有维度的笛卡尔积。只在组合会改变操作、数据保留、权限、副作用或结果时增加组合检查。优先覆盖会阻断任务、丢失工作、重复写入或产生不可逆后果的情况；没有数据时不编造发生概率。

除节点自身的状态外，重点核对相邻转换和交接：有错误页却无法回到可继续的步骤，有成功提示却找不到结果，有重试按钮却重复处理已成功项，都可能是流程断点。每个适用路径应当有可解释的后续或合法终点；用户主动放弃、资源永久删除等终态不必强行返回主流程。

不因通用清单新增产品并不支持的撤销、草稿、离线、取消或自动重试能力。确有用户目标需要时提出产品方案，说明依赖和取舍。

## 4. 区分缺口、提案与待验证

每个发现附位置或场景、进入条件、证据、对任务的影响及最小处理建议，使用以下结论：

- **已验证缺口**：已有要求没有落实、设计内部矛盾，或真实路径出现无合理交代的断点；说明判断依据。
- **待决产品规则**：依据不足以裁定业务行为。主动给出推荐方案、理由和必要的替代方案及代价，明确哪些部分需要用户决定。
- **待验证**：当前材料不能判断覆盖情况或运行结果；指出最小补充证据。
- **已覆盖 / 不适用**：记录支持结论的证据或适用性理由，避免重复提出已有能力。

分支覆盖与问题严重程度分别记录。不要把未验证判为通过，也不为输出问题而制造缺口。截图未显示恢复按钮属于证据不足；源码确认失败后清空尚未保存的输入，且任务要求保留输入，则可据此报告缺口，但不能声称已做运行验证。

建议聚焦最小补全：补条件说明、补必要转换、保留上下文或明确终点。页面结构需重做时交代原因；文案精修、组件选型、视觉质量或任务易用性不是本次审查的完成条件，可记录相关交接项而不展开其他审计。

## 5. 交付审计并等待人工 Review

局部审查用短答或小表给出范围、结论、证据、建议及待决事项。完整审计在目标项目现有文档位置保存 [审计记录](audit-record.md)；无既有位置时使用 `docs/audits/<flow-name>-completeness.md`。无法保存时输出同等可复制内容并说明限制。项目记录不放入本 Skill。

审计阶段的完成条件是：范围内入口、主路径、适用分支和关键交接均已登记；每项有明确的覆盖结论或未验证原因；发现可追溯，产品提案与事实分开，报告已交付。证据不足时可以完成“有验证缺口的审计”，不能宣称“流程完整”或“全部通过”。无问题时如实报告检查范围，不要求制造改动。

**每次新审计在报告交付后必须停在人工 Review 关口。即使用户一开始要求“检查并修复”，也不能在交付报告的同一阶段直接修改业务代码或正式设计。** 告知用户这是本 Skill 的强制阶段规则，并指向本节。报告可以写入；对产品的修复必须等用户看过报告后明确确认实施范围。沉默、时间经过、前期笼统授权和仅认可报告判断，都不等同于实施授权。

如果用户要求调整建议，先更新报告；有审阅意见但尚未授权实施时，保持审计阶段。仅要求审查的任务，报告交付即完成本次请求，无须持续等待或反复催问。

## 6. 人工 Review 后实施与复查

用户审阅报告后明确要求应用已选建议时，沿用该授权直接实施对应事项，不重复要求批准。核对报告基线、当前实现与最新已确认的设计依据；只有影响本次决定的变化才补充审查。新发现的产品取舍或超出已确认范围的修复单独交回 Review，不阻塞无依赖的已批准事项。

用与问题相称的检查验证受影响的入口、转换、结果和上下文保留；需要动态证明的行为不能仅凭代码或构建成功关闭。若环境不支持，记录“已修改，运行待验证”。更新报告中每个发现的处理结果，区分实际修改、已验证结果与剩余依赖。报告确认不自动授权发布、部署或对外发送。

批准的补全若改变范围、主路径、关键业务规则或简报中的假设，同步项目现有设计简报及受影响图稿，标记被替代的决定、变更依据与实际实施状态。仅有新建议时不改写已确认方向；批准但尚未实现的部分明确标为待实施。复用已有事实源，报告引用更新位置；没有简报时无需为此另建一份。后续执行不应仅依据旧简报撤回已经批准的改动。

## 上下文续接与相邻能力

审计过大时按子流程或分支分批更新同一记录，保留稳定 ID、证据基线、已检查范围、未检查队列、未决决定和当前人工 Review 状态。达到上下文限制前先保存这些信息；续接只读取相关记录和变更证据，不重新通读历史或把上轮未检查项算作通过。复杂流程有明确范围内尚未检查的部分时，交付阶段记录而非全量完成结论。

本 Skill 独立可用。项目已有 PRD 查证、设计画布或任务走查产物时可复用其证据：PRD 查证提供需求依据；画布承载流程与分支但不证明正式入口可达；任务走查检查用户是否理解并顺利完成。已有状态表优先增补，不并行维护两套相同事实；不强制安装或运行相邻 Skill。
