# 独立任务走查工作流

本文是执行事实源，[../docs/workflow.svg](../docs/workflow.svg) 是面向人的流程概览。设计与实现完成后，在独立的新会话中，通过可交互原型或运行中的产品检查用户完成任务的实际体验；交付问题报告，等待人工 review。串联设计流程时，本步骤位于流程补全及复查之后、aw-wording-reviewer 文案收敛之前；不把文案审查通过设为走查前提，也不在走查中执行文案规则审计。

## 1. 确定会话、需求与可操作对象

使用未参与本轮设计、实现或前置审查的新会话。不要导入旧会话记录或已有问题报告作为首次走查的指引。若当前会话已经参与上述工作，整理必要需求来源、原型入口和已有任务选择，供用户在新会话启动；不声称可以通过“忽略历史”恢复独立性，也不自行创建会话。用户明确要求在当前会话继续时可以执行，但在报告中注明上下文影响，不能标为独立走查。

有 PRD 时允许完整读取，记录适用版本或来源。没有 PRD 时，使用用户提供的需求、任务说明或设计简报；通过聚焦追问补齐会改变任务选择或成功判定的信息，不要求先补写 PRD。需求冲突或目标不清时，先问清再执行相关任务。文档不可读取与文档未规定分别记录。

设计简报只作为任务选择和覆盖路径规划的辅助依据，权重低于用户当前选定的任务、最新有效需求及实际界面证据。Shaping 中的路径、图稿与取舍理由是待检验的设计方案，不是必须复现的点击路线；不按简报逐步导航，也不因某个障碍有设计理由就否定观察。简报中明确记录的已确认业务规则仍是需求依据，暂用假设不能升格为约束。简报与界面不同可能来自后续批准的修改，先记录差异，再按最新决定核实，不自动要求恢复旧方案。

区分需求知识与界面证据：PRD 可以帮助确定业务规则、目标和预期结果，但文档中写明入口、路径或解释，不代表用户能从界面发现它们。记录已从 PRD、简报或图稿获知的关键路径提示；不能声称第一次独立发现了已读过的路径。无需屏蔽或裁剪完整 PRD。

必须能实际操作当前版本的原型或产品。核实入口、账号角色、运行平台、必要测试数据和允许操作的范围；使用当前环境支持的浏览器或原生界面工具，不绑定产品、工具或供应商。截图和录像可以辅助取证，不能代替交互。只有静态图、工具无法操作、登录不可用或目标服务未就绪时，说明所缺条件并暂停相关走查，不降级成静态推演后宣布完成。环境恢复不属于本 Skill 的修复工作。

已核实隔离的原型中，可在授权任务范围内操作测试数据。原型操作会向真实对象发送消息、产生费用或执行不可逆动作时，使用已有明确授权；缺少授权或隔离证据时暂停该动作，保留其他可独立执行的任务。

## 2. 提出候选任务并由用户选择

根据需求提出少量有代表性的候选任务，兼顾主要目标、重要决策、跨页面衔接或重复工作。范围来自用户目标与需求，不能只根据已有导航推导任务，否则可能漏掉界面未提供的必要能力。不把异常排列组合或遍历每个控件设为任务。

每项候选包括：任务 ID、用户要达成的结果、起始条件、可观察的成功条件，以及选择它的理由。描述结果，不预先提供点击顺序。比如“将三位协作者加入指定项目，其中一位只能查看，并确认结果”，而不是“打开成员页，再点击邀请”。

同时提供三类用户供选择：

| 类型 | 已知条件与检查重点 |
| --- | --- |
| A：懂业务、首次使用产品（默认推荐） | 理解业务对象和专业术语；不预设知道产品导航、专有操作或隐藏规则 |
| B：业务与产品新手 | 需要理解必要业务概念、术语与操作后果 |
| C：熟练用户 | 按已说明的熟悉程度使用产品；重点检查频繁操作、重复劳动、上下文切换与效率 |

请用户选定任务和用户类型；用户只选择任务且未另选类型时采用已告知的默认 A。已有明确选择直接沿用，不重复确认。没有选定任务时不能把候选自动当作批准范围。任务规模过大时提出分批方案，由用户决定本次范围。

不同类型需要分别走查时，分开记录知识假设和路径；同一会话后续尝试已知操作方式，不能冒充新的首次体验。不要虚构人口特征、情绪或经验细节来凑 persona。

## 3. 从界面执行任务并记录第一次尝试

在选定起点开始，仅通过用户可获得的界面、帮助和反馈寻找操作。可以使用可见内容和可访问性树定位控件；不得通过源码、隐藏 DOM、内部状态、网络接口或直接跳转猜测路由来替用户找到入口或完成任务。工具能够定位元素不等于目标用户能够发现它。

不要在任务开始前全面巡览产品、列出标准答案路径或先阅读旧报告。沿实际看到的信息逐步操作，在关键决策处记录当前目标、可见线索、所选操作及其可观察结果；保留误入、返回、求助、重复填写和上下文丢失。重复的输入动作可合并记录，不要求每个按键占一行。

按目标用户的知识，在关键步骤检查：

1. 是否理解此时要达成什么，以及为什么需要这一步。
2. 能否发现相关操作与必要信息。
3. 操作的标签、位置与表现是否让人理解其作用和后果。
4. 操作后是否能知道发生了什么、是否推进目标，以及是否完成。

同时判断整个任务的设计是否合理：步骤是否带来必要价值，跨页面对象与状态是否连续，是否被迫记住或重复输入已有信息，是否需要不必要的往返，完成结果是否满足真实目标。业务上必要的审批、确认和约束不因增加步骤就成为问题；熟练用户的捷径也不自动适用于首次使用者。

允许记录页面职责、流程组织等结构层面的问题，但只描述障碍、条件与影响，不在走查中设计新方案。与任务无关的美观偏好、全面状态枚举、组件规范或文案规则不扩展为本轮专项审计；碰到确实影响任务的问题仍应记录。

## 4. 保存证据，再复现与核实

遇到问题立即保存到目标项目或用户指定的报告位置，使用稳定的问题 ID 关联任务和证据；不把项目报告写入 Skill 目录。记录屏幕、动作前后状态和用户可观察的结果。静态可见问题用截图即可；涉及连续交互、时间或状态变化时使用步骤截图或录像。证据避开账号秘密和无关个人数据。

先保留第一次尝试，再在不会重复产生真实副作用的条件下复现。复现不覆盖首次记录，也不把学会路径后的成功当作首次可发现性通过。不能稳定复现的现象保留发生条件与不确定性，不能直接删除，也不能声称已稳定确认。

分别表达：

- **已观察事实**：实际界面、操作、结果和证据位置。
- **设计影响判断**：为什么这些事实可能阻碍选定类型用户的理解、决策或完成；假设必须说明。
- **待核实条件**：权限、需求冲突、数据条件或原型能力尚不能证明的部分。

首次记录完成后，可按需回查 PRD、向用户澄清或对照已有问题报告，判断是否误报、重复或已知限制；补充核实记录，不回写成“首次就已知道”。不要通过阅读源码转成实现审计。

明确区分原型承诺的可演示行为与真实后端能力。已说明只模拟发送的原型不能证明邮件实际送达，但仍可评价用户是否理解模拟结果。必要步骤无法交互时，报告任务无法验证及其原因；不能把未实现的必需步骤推演为通过，也不要求原型承担未约定的生产能力。

某任务受阻时记录最后可达位置和缺失条件，继续其他独立任务。没有新的可见线索、重试只会重复结果或需要未授权动作时，停止该路径并说明原因，不反复盲试。应用版本或测试数据发生影响路径的变化时，标明新基线并仅重查受影响任务，保留先前证据。

## 5. 交付问题报告，等待人工 review

报告详略匹配任务范围，至少包含：

- **范围与依据**：原型入口和版本线索、需求来源、选定用户类型与已知知识、起点和数据条件、独立会话情况及已知路径提示。
- **任务结果**：每项任务的实际路径与成功条件证据，标为“完成 / 完成但有障碍 / 未完成 / 无法验证”，并解释原因。工具或环境阻塞不直接归因于设计缺陷。
- **问题记录**：问题 ID、相关任务和步骤、观察事实、截图或录像引用、需求依据（适用时）、对理解或任务的影响、复现情况和未决条件。
- **人工 review 项**：需要用户判断的问题、事实冲突和验证缺口；没有则省略。

按任务影响区分阻断、显著负担和轻微障碍，说明理由；合并同一原因在多个任务中的重复表现，保留各处证据。不以问题数量或总分作为完成标准，不编造情绪分数、真实用户成功率或改版收益。

默认交付问题与影响，不提供具体布局、组件、文案或交互修改方案，不修改产品。完成选定范围、保存报告后等待人工 review；用户之后明确要求讨论方案或修复，再沿其选择的范围继续；批准的后续改动影响范围、主路径或关键业务规则时，同步已有设计简报及受影响图稿，记录被替代决定与实际实施状态，问题报告本身不改写已确认方案。若用户明确只要求局部复查，检查对应任务即可，不重跑全产品，也不把已熟悉的路径称为新的独立首次走查。

完成标准：每个选定任务都有结果与证据或明确的无法验证原因，问题可定位，事实与假设区分，未决项已交代，报告已保存并提供访问位置。未完成或无法验证的任务允许形成一份完整报告，但不得据此宣称所有任务通过。范围内没有问题时如实说明，不凑缺陷。Agent 的走查与设计判断不等同于真实用户研究。串联时，人工审阅及获准修复完成后，再由 aw-wording-reviewer 做一致化文案收敛；本 Skill 的只读交付不自动启动后续修改。
