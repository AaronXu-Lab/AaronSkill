# 分档任务派发工作流

本文件是执行事实源，`../docs/workflow.svg` 是面向人的可视化投影。调用本 Skill 的当前会话是主会话；三个持久、用户可见的执行会话分别承担高、中、低档实施任务。主会话负责讨论、资料查询、代码只读调查、盘点、解释、分析、定档和派发；成功派发后即结束本轮，不等待执行完成；不承担已派发实施任务的代码实现或独立复核。接收任务的执行会话在独立分支和 worktree 自行实现、校验、rebase，并依据派发时交付的整合授权与仓库互斥锁，自行完成一次最终整合及预览冒烟检查。主目录承载已验证可用版本，供用户持续浏览。

## 触发和授权

讨论、资料查询、代码只读调查、盘点、解释和分析由主会话直接完成，即使需要调用工具也不派发。例如，盘点组件库中展开收起行为及其实现时，主会话自行读取代码并回答。用户明确要求建立这套工作方式时，才建立执行会话；只有用户要求实际实施、修改或落地执行时，才发送实施任务。用户明确建立本工作方式，授权为指定项目初始化三档本地分支/worktree，以及获派需求完成后的任务提交、rebase 和一次本地合入；沿用该授权，不在每个正常隔离步骤重复确认。仅提及 Skill 名称或只读咨询不构成建立或业务实施授权。授权不包含推送、发布、无关改动的提交、破坏性 reset 或不可恢复清理。

先确认当前使用的平台、目标项目及主会话所在上下文。用平台可用的项目发现能力核对项目身份、主机与仓库信息；不猜测项目标识。不擅自创建项目或定时任务。默认在目标项目所在主机为三档各建立独立分支和 worktree，保持主会话目录、目标分支与模型设置不变。目标分支读取主会话当前实际分支，不硬编码 main/master；主会话为 detached HEAD 或目标不清楚时，仅暂停受影响的初始化/合入并报告。若项目不明确且无法从当前上下文确定，继续可独立完成的讨论，待用户明确项目后再创建。

## 隔离初始化与现有工作迁移

每档初始化时就拥有独立分支和 worktree，即使暂时待命也不共享主目录。记录主会话仓库根目录、主机、目标分支、起点提交与主预览端口，再从该起点建立三份隔离区；不默认从远端默认分支或另一个任务分支开始。使用平台规定的分支前缀，平台没有约定时使用清楚的任务名称。

优先使用平台 managed worktree、会话创建/附加能力，并核实返回的实际目录、Git 分支和起点。工具若返回 detached HEAD，先在该 worktree 建立独立任务分支。平台不能将已有聊天绑定到指定 worktree 时，使用可用 Git 能力准备隔离区，并在后续派发中明确每个命令、文件操作和服务的绝对执行目录；报告 UI cwd 未变，不假装已切换。创建/附加到当前聊天不表示其他聊天已迁移。无法保证执行者使用隔离目录时，不派发写入任务。

代码修改、依赖安装、生成文件、开发服务与测试都在该档 worktree 内进行。依赖目录及可写构建缓存不能 symlink 回主目录；可用工具的只读下载缓存不属于主工作区。每档分配独立且未占用的预览端口，记录进程归属；禁止占用、覆盖或停掉主预览服务，不能因为端口冲突而杀掉其他档位服务。执行者使用自己的浏览器页做验证，不导航用户的主预览标签。合入前主目录只接受已授权且持有仓库互斥锁的最终整合，不边做边复制文件、合入或 cherry-pick 片段。

已有共享目录工作迁移时：

1. 协调者先让现有执行会话到安全检查点停写，取得任务进度、进程与未完成项；执行者不互相读取历史或通信。没有停写确认时，只做不依赖活动状态的独立工作与只读准备，不复制正在变化的目录。
2. 确认停写后，在项目外保存可恢复快照、原 HEAD/分支、已暂存/未暂存补丁、未跟踪文件及删除清单、文件校验和和归属说明。确认快照期间无变化，保留原目录原样；不能自动 stash、reset、批量 commit 或把全部 dirty 认领为某个任务。
3. 可将快照复制到隔离区继续工作，但必须标记为“借用的未提交基线”，记录来源和任务新增差异；复制不是提交授权，也不等于获得干净任务起点。主目录已经包含半成品时，不声称它已成为可用稳定版本；协调者需确定可恢复的已验证基线。
4. 能依据已保存基线精确区分本任务时，只提交本任务差异并在干净整合环境验证。无法区分归属、工作依赖未提交共享基线或安全合入会覆盖 dirty 文件时，报告涉及路径、差异/依赖和候选方案，暂停受影响的提交/合入。由协调者取得所需决定；不得为方便 rebase 把无关基线做成提交。已知安全的独立工作可继续。

## 建立或恢复映射

先查询可见会话和现有映射，核对每个候选会话的平台、项目、身份与实际模型配置；仅在确认属于同一组且仍可用时复用。以下是系列与强度策略，不是固定模型 ID；按当前平台选用同一行，不跨平台混用：

| 平台 | 高档系列 · 强度 | 中档系列 · 强度 | 低档系列 · 强度 |
| --- | --- | --- | --- |
| Codex | Astra · `low` | Sol · `medium` | Luna · `high` |
| Claude | Fable · `low` | Opus · `medium` | Sonnet · `high` |

### 解析当前可用模型

建立、恢复映射及每次实际派发前，都执行以下核对。会话标题、旧映射及本文示例均不能代替平台当前能力证据。

1. **先取用户配置。** 用户显式指定的模型或强度优先，保留其适用范围；指定旧版本也是有效覆盖，不自动升级。仅指定档位或系列时，仍按该系列最新可用版本解析。旧映射中保存的 ID 本身不等于用户锁定版本；覆盖来源不明且会影响选择时先核实。
2. **核对真实能力。** 以目标主机、账号和会话工具当前暴露的模型目录、配置接口或工具参数能力说明为依据，取得准确模型 ID、所属系列、版本先后或 latest / previous 等权威状态、支持的强度及持久会话能力。目录未提供的信息可由平台官方资料补充，但公开发布不证明目标环境可用。不能靠记忆、显示名、名称数字排序或自行拼接 ID 判定系列、版本或能力；不确定的别名不视为已解析。
3. **选择同系列最新可用版本。** 无用户版本覆盖时，在目标环境确认可用的该系列候选中，依据上述版本证据选最新版本；不跨系列替换。只有旧版本可用，且候选范围与版本关系已确认时，可选择它作为“该环境最新可用”，报告可用性限制；只有单个旧 ID 但目录完整性或版本证据不明时，不能声称它最新。用户指定版本时只核对该配置的可用性，不强制升级。
4. **核对强度并处理缺口。** 保留表中的强度或用户显式覆盖。选中模型不支持所需强度时，不回退到支持该强度的旧版本，也不自行改强度或降档。无法确认最新版本、系列、准确 ID、强度或会话能力时，说明已知候选、证据缺口及受影响档位，仅停止受影响的创建或派发，请用户明确替代配置或补充证据；用户指定配置也不能绕过实际能力验证。

例如，平台同时提供 `gpt-6.1-sol`（Latest workhorse）与 `gpt-6-sol`（Previous generation），确认二者属于 Sol 且前者支持 `medium` 时，默认中档解析为 `gpt-6.1-sol` · `medium`。这只是给定目录下的示例，不是未来默认 ID。Claude 对 Sonnet、Opus、Fable 使用同一解析规则；系列名不直接当作可调用 ID，不假定任何未经平台核实的版本号。

### 建立、复用与配置更新

对缺失档位分别创建持久、用户可见的项目会话，显式传入已解析的模型和强度，不能依赖平台默认模型。创建返回排队状态时等待就绪，取得真实会话标识并确认生效配置后才派发。按平台工具要求输出会话创建指令或链接。

恢复映射及每次派发时，将解析出的目标配置与候选会话的实际配置比较：

- 配置一致且可确认时复用。用户手动更改过配置时，按其有效覆盖处理；不能用旧映射覆盖用户的新选择。
- 非用户锁定的旧版本需要更新时，只有平台支持且已有授权涵盖该会话配置更新，才能显式应用新模型与原强度并核实结果。报告旧配置 → 新配置；保留同一会话及上下文，不修改主会话设置。不得中断正在执行的任务来升级，等到下一次获授权的派发边界再核对。
- 平台支持在发送任务时覆盖配置，且本次发送已获授权、配置更新也在授权范围内时，可在同一派发调用中显式传入目标模型与强度。以工具对本次生效配置的确认作为证据；区分单次覆盖与持久默认更新，单次覆盖后后续每次派发仍需显式设置。若平台不能保证目标配置会用于本次执行，则先解决配置问题再发送任务。
- 不能读取或可靠设置配置、平台不支持更新或缺少必要授权时，说明受影响会话和目标配置并等待所需决定；不沿用旧配置派发、不擅自另建替代会话、不把拟更新记为已生效。更新失败或结果不明时核对实际状态，避免重复发送任务。

将平台、项目标识、三个档位的会话标识、主机、实际模型 ID 与强度、选择策略（系列最新 / 用户指定及来源）、能力证据来源与核对时间作为简短映射报告给用户。映射还记录主会话仓库/目标分支/起点、每档绝对 worktree 路径/任务分支/预览端口、未提交基线来源、当前阶段（待命/实施/待整合/已合入）与实际执行目录是否已确认。恢复及每次派发前核对真实 Git 路径、分支、HEAD 与工作区状态；旧路径不存在、已被其他任务使用或残留已合入历史时不能直接沿用。区分持久配置和最近一次派发覆盖；未知字段明确标记，不能伪造。优先依靠已有会话历史、任务附件或项目外的轻量记录恢复，不把协调记录写进业务代码。旧映射只帮助定位会话，不能跳过当前模型解析；无法可靠确认旧映射时先核对，避免重复创建。执行会话之间不得通信、读取彼此历史、相互转派或创建子代理。

## 讨论、定档和派发

先判断任务是否要求实际实施、修改或落地执行。只读请求由主会话完成并直接回答，不因需要研究或调用工具而选择执行档位。实施请求先在主会话澄清目标、实施方向、范围与验收边界。若关键方案仍未明确、会改变用户预期或授权范围，先在主会话讨论清楚，不把复杂未定方案直接交给执行会话；方向与边界明确后，允许执行会话在已讨论范围内形成具体方案并完成实施，按这些剩余判断选档。再按以下顺序决定接收会话：

1. **先按当前任务定档。** 只看这次实施仍有多少不确定性、影响范围和协调复杂度；从当前平台的低档（Codex：Luna · high；Claude：Sonnet · high）是否足够开始判断，再按需升档。区分“按已定方案完成”与“还需形成具体方案再完成”：前者可从低档执行，后者若仍有实质性设计判断则评中档或高档。主会话写出详细派发提示并不证明方案已定，要看关键内容、行为和实施选择是否真正已有结论。原始任务的复杂度不继承给后续任务。
2. **再衡量关联历史的实际收益。** 从主会话已有上下文或获授权的只读会话信息中，识别同组件、同能力或同一改造链条的执行历史，包括已完成任务的后续修正、优化和扩展。仅在复用原会话能显著减少理解成本、衔接风险或迁移风险，且原会话可用、适合本次任务时，倾向原会话。仅同项目、表面相似、同组件名称或历史负责本身，都不足以升档或锁定原会话。选择时简要说明当前任务的档位理由与上下文收益；不用执行会话互读历史。
3. **处理连续补充与明显跃迁。** 当前正在执行的同一修改收到连续补充，可为保留现场上下文、避免打断当前隔离区中的连续修改而继续交给原会话；这不延伸为所有后续任务都留在原档。若原会话不可用，或当前任务的能力、范围明显变化，依当前任务重新选档，并说明具体原因。

| 档位 | 适用实施任务 | 例子 |
| --- | --- | --- |
| 低档：Luna / Sonnet · high | 目标、内容、行为、验收及关键实施方案已明确，剩余是范围有限、路径清楚的局部执行；允许常规实现选择，不要求消除所有细节判断 | 明确方案的 Button 内描边调整；正文和位置已定的文档页；关闭与切换行为已定的窄屏侧栏修复 |
| 中档：Sol / Opus · medium | 在已讨论的方向与边界内，仍需实质性内容组织、语义取舍、去重、信息架构、交互展示设计、适用性判断，或多个相关实现点协调；只改一个页面也可能属于此档 | Button 页 Usage / Composition 的语义、组件边界与共享模板协调；Controls' Gap 交互展示与反馈方案；多个适用组件的 Interactive Demo 迁移 |
| 高档：Astra / Fable · low | 结构性重构、通用能力抽象及迁移，或影响范围广且依赖关系复杂 | 抽象通用 Collapsible 并迁移多个组件 |

例如，Field Container 的跨组件抽取曾由 Astra 实施；后续若只是按明确方案移除 Gallery 的 `control` 属性轴，并将 Preview 改为虚线 Slot 占位，这次是范围清楚的局部任务，应交给 Luna · high，不能继承 Astra 档位。Stat Trend 对齐修正和 Stat Card / Stat Trend 视觉优化若仍牵涉原系列的多个联动实现点，且原 Sol 的上下文能显著减少衔接风险，则可继续交给 Sol；若只是独立的明确样式微调，仍从 Luna 起评。用 [派发回归场景](../tests/dispatch-routing.md) 检查这些边界。

文件数、代码量、验证需求、单页范围及同组件历史均不是独立分档依据：不能据此直接降档或升档。一页任务仍可能需要内容和交互设计；UI 任务也不因含有少量常规判断一律升中档，方案明确的样式、文案和局部交互修复仍适合低档。明确方案后，相似任务可重新评为低档，不按组件或任务名称锁定档位；所有档位都自行完成必要校验。不为平均分配或凑齐档位而轮流派发，关联历史也不能成为把所有任务固定发给 Sol 的理由。不默认提高高档会话的强度。用户指定档位或配置时，在可用且获授权的范围内遵从。

选定接收会话后，按“解析当前可用模型”和“建立、复用与配置更新”复核本次实际生效配置；包括连续补充任务，不能因为复用历史而跳过。派发前核对该档隔离区、基线、端口及进行中任务。隔离实现可以并行，关联变更或依赖另一个未合入需求时按需串行；最终合入由执行者通过共享的仓库互斥锁串行进行，不依赖主会话持续在线。发送给选定会话的一次性实施任务必须自包含，写明目标、已定方案、范围、约束、验收要求、必要项目与文件上下文，以及交付格式。不能假设执行会话知道主会话历史。可用以下简短模板组织交接，删去不适用字段：

```text
目标、已定方向与方案：…
剩余判断与选档理由：已明确的内容、行为和实施选择；执行会话仍需在已讨论边界内完成的设计或协调；为何该档足够。
项目、范围与必要上下文：…
隔离现场：绝对 worktree 路径、任务分支、起点、主会话目标分支、独立预览端口、借用基线及保护清单。
整合安排：完整需求边界、预授权的目标分支与仓库锁绝对路径、锁机制、目标预览冒烟与失败恢复要求。
关联历史（仅有实际收益时）：原会话已处理的相关部分、可复用结论、本次与旧任务的区别；无则省略。
约束和已有授权：…
验收要求与必要校验：…
最终报告：改动、验证证据、未完成项或阻塞；超出原范围或需改变已定方向、方案时在本会话报告。
```

任务授权只覆盖用户已要求的操作；执行会话独立完成实现、必要校验及下述最终整合。执行中发现超范围或需要更改已定方向、方案时，在自身会话报告，不私自与另两个会话通信或转派。派发是自包含实施交接，不设计互查或研究回报流程；整合锁等待由执行者自行处理，不允许执行会话自行相互协商。

### 派发即交付主会话

派发包含从实施到最终交付的完整责任：实现、必要验证与修复、任务提交、rebase、取得整合锁、一次本地合入、主预览冒烟及失败恢复，均由接收任务的执行会话完成。主会话确认平台已接受派发后，简短报告目标会话、实际模型与任务范围，然后立即结束本轮；不能把“已派发”写成“已完成”。不调用等待工具、不轮询进度、不设置监控或提醒，也不为了后续合入保持主会话运行。

执行会话在自己的聊天中报告最终提交、检查、预览结果或具体阻塞，不默认给主会话发消息。主会话仅在用户明确要求查看进度时读取当次快照并回答，除非用户明确要求持续等待，否则不转为盯守。收到补充需求时按本次任务重新定档或转交原执行会话，再结束本轮。需要用户决策的阻塞留在执行会话清楚呈现，不假装完成、不无限重试。

本规则更新默认用于下一次派发；用户要求保留当前任务流程时，不中断或改写已派发任务的整合授权和完成约定。

## 完整需求完成后的单次整合

“一个需求”包含尚未完成时收到的连续补充。执行者在隔离区完成全部实施和必要检查，确认无待实现/待验证项后提交任务分支；开发过程中可有多个可追溯提交，不强制压成一个开发 commit。未完成时只能报告进度或阻塞，不能先将可见的一部分合入主目录。

1. **准备整合与自主串行。** 派发时交付本地整合授权、目标仓库/分支和统一锁位置，无需完成后再等主会话批准。所有档位使用同一个仓库级锁（例如解析 Git common dir 后其中的 `aw-dispatch-integration.lock`），从最终 rebase 前一直持有到合入后冒烟或恢复结束。使用平台可靠互斥机制，或以原子 `mkdir` 取得锁并记录唯一 owner token、任务分支、主机/PID 和取得时间；不能用先检查文件不存在再写入的竞态方式。释放前核对 owner token，仅释放自己的锁。争用时执行会话自行有限等待和退避（单次不超过 60 秒，总等待上限随派发明确，默认 10 分钟）；超时在执行会话报告待整合，不唤醒或占用主会话。未知或疑似过期的锁不按时间强抢；验证原执行者已停止且主目录安全后才能恢复，不能确定则报告阻塞。合入冒烟失败时保留阻塞标记，阻止后续执行者越过失败现场。锁记录仅用于文件级互斥，不授权执行会话通信或读取彼此历史。
2. **更新任务基线。** 在干净任务分支 rebase 到主会话目标分支的最新本地 HEAD，记录具体 SHA。执行者解决范围内冲突并复核任务意图，运行受影响检查及必要完整验证。冲突涉及超范围决策或借用基线归属时报告并暂停，不把主目录拿来试错。不使用自动 stash 掩盖未提交状态。
3. **守住最终边界。** 合入前再次确认目标 HEAD 未变、目标工作区没有会被覆盖的修改且仓库整合锁仍归本需求。HEAD 已变化则重新 rebase 并重跑受影响检查；目标 dirty 不被自动清理或打包提交，即使 Git 允许也核对不相关文件能原样保留。需要验证与任务共同生效的未提交内容但无法安全重建时报告阻塞。
4. **一次本地合入。** 完成上述校验后，在目标分支执行一次保留任务来源的整合；默认使用 `merge --no-ff` 创建一个需求级 merge commit，记录目标前后 SHA、任务分支和验证基线。项目另有策略时遵从，但每需求只有一个最终整合事件，不用零散 cherry-pick 或边开发边合。任务分支的多个开发提交可保留。
5. **预览冒烟与恢复。** 合入后由执行者在自己浏览器页对目标预览做适用冒烟检查，核对响应、关键页面和必要参数/锚点。不得抢占或停止主预览端口；若服务需要重载而平台无法无中断完成，先报告明确限制，在执行会话报告并依已有明确维护授权处理。冒烟失败立即停止本需求之后的其他合入，在不丢任务成果/用户 dirty 的前提下恢复已验证状态：优先在目标 HEAD 仍为本次整合且范围明确时 revert 此 merge；不能安全恢复则保留快照和分支、报告精确阻塞，不强制 reset。恢复不算成功完成，修复并清除明确归属的阻塞后重新取得锁、验证交付。

后续独立需求复用持久聊天上下文，但从目标分支最新 HEAD 建立新的干净任务分支/worktree。可以保留该档环境和依赖，在干净 worktree 中切换新任务分支；不能在已合入旧任务分支继续追加，或让旧任务未归属文件混入新需求。保留旧分支/可恢复快照，清理只在已有授权和可恢复保障下进行；managed worktree 用对应 archive 工具。连续补充尚属同一未完成需求时保留当前分支，不提前合入。

## 停止与交付

讨论或只读调查阶段由主会话直接交付答案或明确方案。建立阶段交付三档会话与隔离路径映射、实际执行目录确认、基线来源、模型选择依据和不可用项。实施派发阶段，主会话仅交付目标会话、档位、实际模型与强度、配置变化和任务摘要，并结束本轮。执行会话负责最终交付改动、验证证据、rebase 基线、一次整合的 commit/目标前后 SHA、预览冒烟与恢复结果及遗留问题。锁争用超时、dirty 归属未决或预览未通过时，由执行会话明确区分“隔离实现完成”与“需求已合入可用”。用户之后要求进度时，主会话可读取并转述现有结果，不另做独立复核。若关键方案尚未明确，主会话继续讨论后再定档派发；若缺少必要授权、目标项目或可用模型，仅停止受影响的创建或派发，说明所需用户决定。
