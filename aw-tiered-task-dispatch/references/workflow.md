# 分档任务派发工作流

本文件是执行事实源，`../docs/workflow.svg` 是面向人的可视化投影。调用本 Skill 的当前会话是主会话；三个持久、用户可见的执行会话分别承担高、中、低档实施任务。主会话负责讨论、资料查询、代码只读调查、盘点、解释、分析、定档、派发和转述结果；不承担已派发实施任务的代码实现或独立复核。接收任务的执行会话自行实现、校验并报告。

## 触发和授权

讨论、资料查询、代码只读调查、盘点、解释和分析由主会话直接完成，即使需要调用工具也不派发。例如，盘点组件库中展开收起行为及其实现时，主会话自行读取代码并回答。用户明确要求建立这套工作方式时，才建立执行会话；只有用户要求实际实施、修改或落地执行时，才发送实施任务。Skill 名称的调用本身不扩大用户对具体项目写入、外部操作、提交或发布的授权。沿用已给出的授权，不重复询问。

先确认当前使用的平台、目标项目及主会话所在上下文。用平台可用的项目发现能力核对项目身份、主机与仓库信息；不猜测项目标识。不擅自创建项目、worktree、分支或定时任务。默认在项目现有本地环境建立三个会话，主会话的模型设置不变。若项目不明确且无法从当前上下文确定，继续可独立完成的讨论，待用户明确项目后再创建。

## 建立或恢复映射

先查询可见会话和现有映射，核对每个候选会话的平台、项目、身份与实际模型配置；仅在确认属于同一组且仍可用时复用。以下是系列与强度策略，不是固定模型 ID；按当前平台选用同一行，不跨平台混用：

| 平台 | 高档系列 · 强度 | 中档系列 · 强度 | 低档系列 · 强度 |
| --- | --- | --- | --- |
| Codex | Astra · `low` | Sol · `medium` | Luna · `high` |
| Claude | Fable · `low` | Opus · `medium` | Sonnet · `high` |

### 解析当前可用模型

建立、恢复映射及每次实际派发前，都执行以下核对。会话标题、旧映射及本文示例均不能代替平台当前能力证据。

1. **先取用户配置。** 用户显式指定的模型或强度优先，保留其适用范围；指定旧版本也是有效覆盖，不自动升级。仅指定档位或系列时，仍按该系列最新可用版本解析。旧映射中保存的 ID 本身不等于用户锁定版本；覆盖来源不明且会影响选择时先核实。
2. **核对真实能力。** 以目标主机、账号和会话工具当前暴露的模型目录、配置接口或工具参数能力说明为依据，取得准确模型 ID、所属系列、版本先后或 latest / previous 等权威状态、支持的强度及持久会话能力。目录未提供的信息可由平台官方资料补充，但公开发布不证明目标环境可用。不能靠记忆、显示名、名称数字排序或自行拼接 ID 判定系列、版本或能力；不确定的别名不视为已解析。
3. **选择同系列最新可用版本。** 无用户版本覆盖时，在目标环境确认可用的该系列候选中，依据上述版本证据选最新版本；不跨系列替换。只有旧版本可用，且候选范围与版本关系已确认时，可选择它作为“该环境最新可用”，报告可用性限制；只有单个旧 ID 但目录完整性或版本证据不明时，不能声称它最新。用户指定版本时只核对该配置的可用性，不强制升级。
4. **核对强度并处理缺口。** 保留表中的强度或用户显式覆盖。选中模型不支持所需强度时，不回退到支持该强度的旧版本，也不自行改强度或降档。无法确认最新版本、系列、准确 ID、强度或会话能力时，说明已知候选、证据缺口及受影响档位，仅停止受影响的创建或派发，请用户明确替代配置或补充证据；用户指定配置也不能绕过实际能力验证。

例如，平台同时提供 `gpt-6.1-sol`（Latest workhorse）与 `gpt-6-sol`（Previous generation），确认二者属于 Sol 且前者支持 `medium` 时，默认中档解析为 `gpt-6.1-sol` · `medium`。这只是给定目录下的示例，不是未来默认 ID。Claude 对 Sonnet、Opus、Fable 使用同一解析规则；系列名不直接当作可调用 ID，不假定任何未经平台核实的版本号。

### 建立、复用与配置更新

对缺失档位分别创建持久、用户可见的项目会话，显式传入已解析的模型和强度，不能依赖平台默认模型。创建返回排队状态时等待就绪，取得真实会话标识并确认生效配置后才派发。按平台工具要求输出会话创建指令或链接。

恢复映射及每次派发时，将解析出的目标配置与候选会话的实际配置比较：

- 配置一致且可确认时复用。用户手动更改过配置时，按其有效覆盖处理；不能用旧映射覆盖用户的新选择。
- 非用户锁定的旧版本需要更新时，只有平台支持且已有授权涵盖该会话配置更新，才能显式应用新模型与原强度并核实结果。报告旧配置 → 新配置；保留同一会话及上下文，不修改主会话设置。不得中断正在执行的任务来升级，等到下一次获授权的派发边界再核对。
- 平台支持在发送任务时覆盖配置，且本次发送已获授权、配置更新也在授权范围内时，可在同一派发调用中显式传入目标模型与强度。以工具对本次生效配置的确认作为证据；区分单次覆盖与持久默认更新，单次覆盖后后续每次派发仍需显式设置。若平台不能保证目标配置会用于本次执行，则先解决配置问题再发送任务。
- 不能读取或可靠设置配置、平台不支持更新或缺少必要授权时，说明受影响会话和目标配置并等待所需决定；不沿用旧配置派发、不擅自另建替代会话、不把拟更新记为已生效。更新失败或结果不明时核对实际状态，避免重复发送任务。

将平台、项目标识、三个档位的会话标识、可用的主机标识、实际模型 ID 与强度、选择策略（系列最新 / 用户指定及来源）、能力证据来源与核对时间作为简短映射报告给用户。区分持久配置和最近一次派发覆盖；未知字段明确标记，不能伪造。优先依靠已有会话历史、任务附件或项目外的轻量记录恢复，不把协调记录写进业务代码。旧映射只帮助定位会话，不能跳过当前模型解析；无法可靠确认旧映射时先核对，避免重复创建。执行会话之间不得通信、读取彼此历史、相互转派或创建子代理。

## 讨论、定档和派发

先判断任务是否要求实际实施、修改或落地执行。只读请求由主会话完成并直接回答，不因需要研究或调用工具而选择执行档位。实施请求先在主会话澄清目标、实施方向、范围与验收边界。若关键方案仍未明确、会改变用户预期或授权范围，先在主会话讨论清楚，不把复杂未定方案直接交给执行会话；方向与边界明确后，允许执行会话在已讨论范围内形成具体方案并完成实施，按这些剩余判断选档。再按以下顺序决定接收会话：

1. **先按当前任务定档。** 只看这次实施仍有多少不确定性、影响范围和协调复杂度；从当前平台的低档（Codex：Luna · high；Claude：Sonnet · high）是否足够开始判断，再按需升档。区分“按已定方案完成”与“还需形成具体方案再完成”：前者可从低档执行，后者若仍有实质性设计判断则评中档或高档。主会话写出详细派发提示并不证明方案已定，要看关键内容、行为和实施选择是否真正已有结论。原始任务的复杂度不继承给后续任务。
2. **再衡量关联历史的实际收益。** 从主会话已有上下文或获授权的只读会话信息中，识别同组件、同能力或同一改造链条的执行历史，包括已完成任务的后续修正、优化和扩展。仅在复用原会话能显著减少理解成本、衔接风险或迁移风险，且原会话可用、适合本次任务时，倾向原会话。仅同项目、表面相似、同组件名称或历史负责本身，都不足以升档或锁定原会话。选择时简要说明当前任务的档位理由与上下文收益；不用执行会话互读历史。
3. **处理连续补充与明显跃迁。** 当前正在执行的同一修改收到连续补充，可为保留现场上下文、避免共享目录冲突而继续交给原会话；这不延伸为所有后续任务都留在原档。若原会话不可用，或当前任务的能力、范围明显变化，依当前任务重新选档，并说明具体原因。

| 档位 | 适用实施任务 | 例子 |
| --- | --- | --- |
| 低档：Luna / Sonnet · high | 目标、内容、行为、验收及关键实施方案已明确，剩余是范围有限、路径清楚的局部执行；允许常规实现选择，不要求消除所有细节判断 | 明确方案的 Button 内描边调整；正文和位置已定的文档页；关闭与切换行为已定的窄屏侧栏修复 |
| 中档：Sol / Opus · medium | 在已讨论的方向与边界内，仍需实质性内容组织、语义取舍、去重、信息架构、交互展示设计、适用性判断，或多个相关实现点协调；只改一个页面也可能属于此档 | Button 页 Usage / Composition 的语义、组件边界与共享模板协调；Controls' Gap 交互展示与反馈方案；多个适用组件的 Interactive Demo 迁移 |
| 高档：Astra / Fable · low | 结构性重构、通用能力抽象及迁移，或影响范围广且依赖关系复杂 | 抽象通用 Collapsible 并迁移多个组件 |

例如，Field Container 的跨组件抽取曾由 Astra 实施；后续若只是按明确方案移除 Gallery 的 `control` 属性轴，并将 Preview 改为虚线 Slot 占位，这次是范围清楚的局部任务，应交给 Luna · high，不能继承 Astra 档位。Stat Trend 对齐修正和 Stat Card / Stat Trend 视觉优化若仍牵涉原系列的多个联动实现点，且原 Sol 的上下文能显著减少衔接风险，则可继续交给 Sol；若只是独立的明确样式微调，仍从 Luna 起评。用 [派发回归场景](../tests/dispatch-routing.md) 检查这些边界。

文件数、代码量、验证需求、单页范围及同组件历史均不是独立分档依据：不能据此直接降档或升档。一页任务仍可能需要内容和交互设计；UI 任务也不因含有少量常规判断一律升中档，方案明确的样式、文案和局部交互修复仍适合低档。明确方案后，相似任务可重新评为低档，不按组件或任务名称锁定档位；所有档位都自行完成必要校验。不为平均分配或凑齐档位而轮流派发，关联历史也不能成为把所有任务固定发给 Sol 的理由。不默认提高高档会话的强度。用户指定档位或配置时，在可用且获授权的范围内遵从。

选定接收会话后，按“解析当前可用模型”和“建立、复用与配置更新”复核本次实际生效配置；包括连续补充任务，不能因为复用历史而跳过。派发前检查共享目录中的进行中任务，避免重叠写入；有重叠时按需串行。发送给选定会话的一次性实施任务必须自包含，写明目标、已定方案、范围、约束、验收要求、必要项目与文件上下文，以及交付格式。不能假设执行会话知道主会话历史。可用以下简短模板组织交接，删去不适用字段：

```text
目标、已定方向与方案：…
剩余判断与选档理由：已明确的内容、行为和实施选择；执行会话仍需在已讨论边界内完成的设计或协调；为何该档足够。
项目、范围与必要上下文：…
关联历史（仅有实际收益时）：原会话已处理的相关部分、可复用结论、本次与旧任务的区别；无则省略。
约束和已有授权：…
验收要求与必要校验：…
最终报告：改动、验证证据、未完成项或阻塞；超出原范围或需改变已定方向、方案时在本会话报告。
```

任务授权只覆盖用户已要求的操作；执行会话独立完成实现与必要校验。执行中发现超范围或需要更改已定方向、方案时，在自身会话报告，不私自与另两个会话通信或转派。派发是单向交接，不设计需要往返查询或等待研究回报的委派流程。

主会话可以按需要读取或等待执行状态，把结果和下一步转述给用户；读取状态不构成独立复核。不默认轮询、设置提醒或自动重试。每次派发都按本次任务重新定档并补足自包含上下文，不主动延续旧任务；连续补充按上述例外处理。主会话不因执行会话完成就自行补做实现。

## 停止与交付

讨论或只读调查阶段由主会话直接交付答案或明确方案。建立阶段交付三档会话映射、模型选择依据和不可用项。实施派发阶段交付目标会话、档位、实际模型与强度、配置变化和任务摘要；执行结束时转述其改动、验证证据及遗留问题，并说明这些证据由执行会话提供。若关键方案尚未明确，主会话继续讨论后再定档派发；若缺少必要授权、目标项目或可用模型，仅停止受影响的创建或派发，说明所需用户决定。
