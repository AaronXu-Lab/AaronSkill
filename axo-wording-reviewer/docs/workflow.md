# AXO Wording Reviewer 文本工作流

本文件是执行事实源。`workflow.svg` 是与本文件同步的可视化投影，仅在生成、更新或视觉核对流程图时才需要读取。

## 阶段 1：收集项目专有约束

**先收集，才有东西可确认。** 本阶段不与用户交互，只把这次审查需要的项目侧信息取全。

从用户提到的项目或目录定位仓库根——这里只需要粗定位，精确的审查范围留到阶段 3。然后收集三样东西：

1. **命名禁令**。脚本从给定路径向上查找 `AGENTS.md` / `CLAUDE.md` / `AGENTS.design.md`，识别「不允许出现 X」这类句式：

   ```bash
   python3 <本 SKILL 目录>/scripts/check_copy.py <项目路径> --list-bans
   ```

   输出分两段：**文案禁用词**直接参与扫描；**只约束代码命名的禁令**单独列出、默认不参与——判据是句子里有「工程代码」「标识符」「变量」「文件名」这类信号而没有「文案」「界面」信号。后者是代码规范，写成变量名与文件名，通常不会出现在界面上；用户明确要审时用 `--ban <TERM>` 提回来。

   提取是启发式的：只取拉丁标识符与引号包裹的词，跳过代码约束（`useContext`、`console.log`）与范畴描述（「禁止使用炒作话术」）。**它会漏掉项目里以自然语言表述的禁令**——通读这些文档，把脚本没抓到的记下来。

2. **将启用的规则集**：

   ```bash
   python3 <本 SKILL 目录>/scripts/check_copy.py --list-rules
   ```

3. **项目专有约束**。读项目文档里的术语表、状态词集合、占位数据约定与语气规范，登记下来供阶段 5 判定。本 SKILL 只承载通用规则，不替项目决定这些——项目侧的约定与 [references/rules.md](../references/rules.md) 的通用规则合并后一起执行，冲突时以项目为准。

**判断：** 项目没有任何成文约束（找不到 `AGENTS.md` / `CLAUDE.md` / 设计文档）时不停止——记为「无项目专有约束」，只按本 SKILL 的通用规则审查，并在阶段 2 如实告知用户。

## 阶段 2：预检与确认（开始扫描前的许可闸门）

**在确定审查范围、正式扫描之前完成本阶段。** 把阶段 1 收集到的东西完整摆给用户看，让用户先知道「这次会按什么规则、拿什么禁用词来审」。

逐条列出：

- 提取到哪些文案禁用词，各自出自哪个文件的哪一行；
- 哪些禁令因为只约束代码命名被跳过，用户是否要用 `--ban` 提回来；
- 通读文档后补记的、脚本抓不到的禁令；
- 会启用哪些规则；
- 登记到哪些项目专有约束（术语表、状态词、占位约定），或明确说明没有。

然后**取得许可后再继续**。

**用户可以选择性执行**，把选择落到参数上：

| 用户的选择 | 参数 |
| --- | --- |
| 不查某条规则 | `--skip-rule <ID>`，可重复 |
| 只查某几条规则 | `--rule <ID>`，可重复 |
| 排除某个被误提取的禁用词 | `--skip-ban <TERM>`，可重复 |
| 补一个脚本没抓到的禁用词 | `--ban <TERM>`，可重复 |
| 禁令来源抓错了 | `--agents-md <文件>` 指定，或 `--no-agents-md` 关闭 |

**停止条件：**

- 用户未许可，或只许可了一部分 → 只执行获准的部分，不扩大到未获准的规则与禁用词。
- 用户完全未回应 → 不开始扫描。

## 阶段 3：确定审查范围

确定要审查的文案集合，按以下优先级取第一个成立的：

1. 用户显式给出的文件、目录、页面路由或粘贴的文案片段。
2. 当前工作区未提交改动中含中文字符串的文件。
3. 用户点名的业务域，映射到对应的页面目录与 i18n 中文词条。

**停止条件：**

- 范围解析为空 → 停止，说明没有可审查的中文文案，请用户指明目标。
- 目标只含非简体中文语料 → 本 SKILL 的排版规则以简体中文为准，说明不适用并停止。
- 范围会跨出用户指定的子工程或仓库 → 先说明范围并等用户确认。

## 阶段 4：机械检查

按阶段 2 获准的规则与禁用词运行：

```bash
python3 <本 SKILL 目录>/scripts/check_copy.py <范围路径> --json [用户选择的 --skip-rule / --skip-ban 等]
```

脚本只报告不改文件。输出分两级：

- `error`：违反即需修改。
- `warn`：真实但存在合理例外，需要逐条判断。

多语言项目只会检查简体中文语料，其余语言目录自动跳过。

首次在新仓库或改动脚本后，先跑 `python3 <本 SKILL 目录>/scripts/check_copy.py --self-check` 确认规则集完好。

**判断：** 脚本零命中不等于通过，只说明可机械判定的部分没问题；必须继续阶段 5。

## 阶段 5：人工复核不可机械判定的规则



读 [references/rules.md](../references/rules.md)，对范围内每条文案逐项核对标记为「人工」的规则族：

- ` · ` 链的段位数量与空段过滤（B4 / B5）。
- 说明性文案的句末句号：脚本只判标签与按钮，`description` 成句与否逐条看（C6）。
- 日期时间的模式选择：relative / absolute / hybrid 是否与该信息流的用户任务匹配，同一列表内是否混用（D2）。
- 名称与术语：name-casing.csv 表外的品牌与产品实体名、同义词是否漂移（E1 / E2）。
- 语气与人称：是否紧凑理性、产品是否自称「我们」、是否用「它」指代对象（F2 / F3）。
- 微文案形状：按钮、确认弹窗、空状态两语域、错误、toast、占位符、标题（G1–G9）。
- 阶段 1 登记的项目专有约束，以及脚本抓不到、阶段 2 已告知用户的禁令。

**判断：** 需要产品事实才能裁定的措辞（业务对象叫什么、状态含义），以项目的产品规格为准；查不到就标记为待确认，不要自行编造。

## 阶段 6：日期时间格式化器的迁移判断

**仅当**阶段 4 或阶段 5 发现目标项目在页面里手写日期格式、或存在多套格式化逻辑时进入本阶段。

1. 在报告中说明现状：有哪些手写格式、分布在哪些文件。
2. 说明本 SKILL 内置的 [assets/format-time.ts](../assets/format-time.ts) 可整份迁移，无依赖、无框架绑定。
3. **征求用户许可。**

**停止条件：** 用户未明确同意 → 只报告不迁移，进入阶段 7。

获准后：把该文件复制到项目约定的工具目录，按项目的导入风格调整路径与命名（需要其他语言时通过 `labels` 覆盖默认中文标签），把散落的手写格式逐处替换为 `formatTimeDisplay`，改动后运行项目自身的类型检查。

## 阶段 7：分级与报告

产出一份清单，每条包含：

- `file:line`
- 规则 ID 与级别
- 原文案（逐字引用）
- 建议改写（逐字给出替换后的完整字符串）
- 依据（`references/rules.md` 的规则 ID，或项目文档的章节）

按 `error` → `warn` → 建议排序。个人偏好不得计入 `error`。

**停止条件：** 到此为止即为一次完整 Review。除非用户要求修改，不要动文件。

## 阶段 8：按需应用修改

仅在用户明确要求修改时执行：

1. 只改文案字符串，不动组件结构、样式、类型与接口契约。
2. i18n key 保持不变，只改 value。改简体中文后，同一 key 的其他语言若语义随之变化，一并说明，但不代译。
3. 重跑 `python3 <本 SKILL 目录>/scripts/check_copy.py <范围路径>` 确认新增违例为零。
4. 涉及类型化源码时运行项目自身的类型检查。

**最终产物：** 一份带 `file:line`、规则依据和逐字改写建议的 Review 报告；用户要求时附带已应用的文案改动、可选的格式化器迁移与验证结果。
