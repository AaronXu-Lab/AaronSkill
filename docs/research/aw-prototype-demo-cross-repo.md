# 本地 AXO 原型同步到 GitHub 的 Skill 研究

2026-11-21 · 方案研究

## 职责与来源

这个 Skill 只负责把**本地最新、已选定为可交付的原型成果**同步到 GitHub 私有仓库 `AaronXu-Lab/untitled2`。本地原型是内容事实源。GitHub 目标分支用于确认上次发布、识别远端独有变化和验证写入结果。正式项目分支、PRD、真实后端契约和产品适配由本地原型开发流程处理，均无需作为本 Skill 的输入。

本地最新版本要从用户指定的原型目录确认。它可能包含已提交、已暂存、未暂存和未跟踪的成果。同步前按明确的交付范围读取实际文件，以当前工作目录中选定文件的内容为候选，保留其他任务的改动。未提交内容可以属于本次交付，但需要可审查的路径范围。若同一文件在暂存区和工作目录有不同版本，以工作目录最新版本为默认候选并在差异中明确，避免把暂存区误当作最终成果。

目前核对到 `aw-prototype-demo` 安装版为 `1.0.0`，主要职责是构建、扩展和验证纯本地交互原型。当前原型现场在 `/Users/wally/.codex/worktrees/prototype-experience/axo-app-fe`，其中包含大量未提交成果。迁移完成后，在项目配置中把同步源改为用户指定的长期本地原型目录。这次研究未核验 GitHub 目标分支或远端内容。 [现有 Skill](/Users/wally/.codex/skills/aw-prototype-demo/SKILL.md) · [现有原型台账](/Users/wally/.codex/worktrees/prototype-experience/axo-app-fe/output/ai_generates/prototype-experience-20261111/coverage.md:216)

## Skill 归属

现有 `aw-prototype-demo` 已有本地开发用法。建议新建一个单用途同步 Skill，初始版本 `1.0.0`，命名可用 `aw-prototype-sync`。触发条件是用户明确要求把现有本地原型同步、更新或预演到 GitHub。现有 Skill 继续服务原型开发。若用户明确要将现有 Skill 改成同步专用，职责替换会改变现有调用契约，需另行确定版本和替换方式。

未来纳入 AaronSkill 可归「工具类」。按仓库规范维护 `SKILL.md`、`references/workflow.md`、`docs/workflow.svg`，同步两份 README 的分类、版本和数量。先写文本工作流，再同步 SVG 和入口，最后执行基础校验和 AW 校验，并预览 SVG。GitHub 目标由功能和配置声明，保留对执行工具的选择，不添加供应商专属元数据文件。 [仓库规范](/Users/wally/Documents/AaronSkill/AGENTS.md) · [AW 维护契约](/Users/wally/Documents/AaronSkill/aw-meta-skill/references/workflow.md)

## 同步契约

| 项目 | 最小约定 |
| --- | --- |
| 本地来源 | 原型根目录、导出路径范围、可选的用户点名新增路径、现有启动和验证入口 |
| GitHub 目标 | 仓库标识、目标分支及目标 checkout。首次执行读取实际分支状态，确认仓库身份和可写权限 |
| 路径规则 | 保持目标目录结构，或使用显式的相对路径映射。校验路径、符号链接和嵌套仓库，保护 README、仓库配置等目标专有内容 |
| 交付内容 | 原型代码、已审核的合成 fixtures、稳定运行所需的锁文件、资产及说明。排除本机配置、凭证、真实业务地址、用户或业务数据、缓存、录屏和运行态产物 |
| 已同步记录 | 只保留一个当前发布记录，包含上次确认的远端 SHA、已发布路径范围、对应本地候选与完成状态。候选以目标 Git tree 或可回读差异标识，支持未提交来源 |

1. **冻结本次本地候选。** 校验两端目录和目标分支，读取上次发布记录，对纳入路径进行增删改与重命名比较。已经配置且明确纳入的本地删除可生成目标删除；忽略规则变化、目录缺失或映射调整引起的批量消失先确认。源端不用提交、切分支或重置。冻结后发现本地又变化，报告这次发布的候选与更新差异，避免把新旧文件混入同一候选。
2. **核对远端独有变化。** 比较上次确认的 GitHub 版本、本次本地候选和当前远端。互不影响的远端变化可以保留；同路径冲突说明哪部分来自拍板的本地原型、哪部分在 GitHub 独有，先处理冲突再发布相应内容。目标专有文件按配置保护。正常推送若遭遇分支推进，重新读取并比较后才继续。
3. **检查候选。** 审查发布差异及排除项。若原型代码和依赖与本地已验候选一致，继承适用结果；依赖、构建或网络配置有变化时运行相应构建及隔离检查；关键交互变化且缺少对应证据时，只验证受影响的一条主旅程。纯同步无需补开发阶段未选择的产品分支。使用 Playwright 时在清理阶段关闭本轮具名会话。
4. **发布与读回。** 预演只交付要同步的差异、排除项和冲突。执行模式按授权提交并正常推送到指定分支，随后读回远端 SHA 和候选内容。推送结果未知时先读回，已到达候选 SHA 就记为完成；远端有新提交时验证候选是否已包含并检查差异，避免重放已受理操作。只有发布读回成功才推进基线。无变化时交付候选与 GitHub 已一致的证据，无需空提交。
