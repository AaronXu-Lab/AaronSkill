# Aaron 文风改写

把任务理解为“恢复作者的思考方式”，不要理解为“添加 Aaron 常用词”。

## 先读取这些资料

每次执行都完整读取：

- [references/voice-model.md](references/voice-model.md)：理解文风背后的认知姿态和语言功能。
- [references/anti-slop.md](references/anti-slop.md)：执行通用反 AI 规则和“伪 Aaron 化”硬约束。

根据文章类型读取：

- [references/modes.md](references/modes.md)：选择与体裁匹配的组织方式。
- [references/examples.md](references/examples.md)：遇到重度 AI 稿、只有笔记、或难以判断改写力度时，参考正反例。

仅在用户要求重新分析博客、刷新文风或解释语料依据时读取：

- [references/corpus-calibration.md](references/corpus-calibration.md)：按时间、原创性和体裁更新语料权重。

## 工作原则

1. 优先保留作者的判断，其次才是句子风格。
2. 优先恢复真实的思考路径，不要只做同义词替换。
3. 把第一人称当作信息来源标记，不要当作“人味装饰”。
4. 把口语、反问、短句和英文词当作功能性工具，不要当作身份标签。
5. 允许文字保留一点正在思考的质感，但清理笔误、重复和无意的混乱。
6. 写得像 Aaron 在当前状态下会写出的新文章，不要拼贴旧文章的句子。

## 改写流程

### 1. 建立不可改动清单

先在内部区分：

- 已确认的事实、数字、时间、产品名和引用。
- 作者亲历的行为与感受。
- 作者明确表达的判断和偏好。
- 作者标为猜测、可能或尚未验证的内容。
- 外部来源的观点。
- 原稿没有提供的信息。

禁止把这些类别互相转换。尤其不要把推测写成事实，不要把外部观点写成作者亲历，不要为增加人味而编造场景、情绪、对话、数字或失败经历。

### 2. 识别文章模式

从 `modes.md` 选择一个主模式，必要时加一个辅模式。不要因为 Aaron 是设计师，就把所有文章都改成产品分析。

同时判断语气强度：

- 低：资讯、教程、说明。
- 中：实践复盘、产品体验。
- 高：观点评论、个人或文化评论。

不得把语气强度改得高于原稿所支持的程度。

### 3. 找回文章真正要解决的问题

在内部回答：

- 什么具体经历、产品或困惑触发了这篇文章？
- 作者原先怎么想，后来被什么细节改变了判断？
- 文章最重要的矛盾是什么？
- 哪些内容来自观察，哪些只是解释或猜测？
- 读完后，作者希望读者看到什么问题、做出什么判断或采取什么行动？

如果原稿没有“转变”，不要硬造转变。如果只是教程，就围绕任务和踩坑组织。

### 4. 重建论证，再处理语言

先删除聊天残留、宏大开场、泛化意义、假权威、模板化三段式、重复总结和无依据的乐观结尾。

再按以下顺序重建：

1. 用具体触发点或核心判断进入文章。
2. 保留能证明作者确实做过、看过、测过的细节。
3. 让每个抽象判断后面都有案例、机制、成本或边界。
4. 明确标记观察、推测和结论之间的距离。
5. 让建议包含适用条件、代价或验证方式。
6. 在论证自然结束的地方收尾，不强求升华。

### 5. 做一次克制的声音校准

只在有功能时使用这些手段：

- 用“我发现”“我后来”“我的判断是”标记认识来源或变化。
- 用口语转折降低连续技术解释的密度。
- 用短句落下已经论证完成的判断。
- 用生活化类比解释抽象机制。
- 保留必要的行业英文，以维持精确度。
- 在真实困惑处提出问题，并在后文处理它。

每次使用前都问：“删掉这个特征，逻辑或情绪是否会受损？”如果不会，删掉。

### 6. 执行反 Slop 审计

逐条检查 `anti-slop.md`。处理本地文件时，再运行：

```bash
node scripts/audit-style.mjs --source <原稿路径> <改写稿路径>
```

只有内联文本时，在内部执行同样的比较。脚本只负责发现表面风险，最终判断仍以语义功能为准。

至少完成两轮：

- 第一轮检查通用 AI 痕迹。
- 第二轮专门检查是否为了“像 Aaron”而过度添加第一人称、口头禅、反问、英文、俚语、括号和金句。

如果改写稿比原稿更像在表演一种人格，回退。

### 7. 交付

默认只输出可直接使用的终稿。

仅在用户要求审阅过程、原稿存在事实缺口或改动会影响立场时，额外输出简短说明。不要默认交付“草稿、审计、终稿”三份冗长内容。

## 输入处理

- 对完整 Markdown：保留 frontmatter、链接、引用、代码块、图片和合法标题层级，除非用户要求调整结构。
- 对纯文本：保留段落语义，不擅自增加 Markdown 装饰。
- 对零散笔记：可调整顺序和补连接，但不得补写作者没有提供的观点或经历；用明确占位符标记真正缺失的关键信息。
- 对引用和数据：保留出处与不确定性；无法验证时，不用“专家认为”等话术遮掩。
- 对已经很像 Aaron 的段落：少改。不要为了显示 Skill 生效而重写正常的人类表达。

## 完成标准

交付前确认：

- 事实、立场、经历和不确定性均未漂移。
- 文章能看出作者为什么会形成这个判断。
- 具体细节承担了论证，而不是仅作装饰。
- 语言强度与体裁相符。
- 没有明显通用 AI 模板。
- 没有明显 Aaron 模仿秀。
- 结尾由正文推导出来，没有临时制造金句。
