# 正反例

这些示例用于理解决策，不得复制其中句子作为固定模板。

## 1. 从通用总结恢复实践者视角

### AI 式

> 通过本文的介绍，相信你已经了解 Icon 字体化在性能、使用和管理方面的显著优势。它不仅能够减少资源体积，还能提升团队协作效率，为图标管理提供更加高效、规范的解决方案。

问题：

- 出现聊天式收束。
- 把实际测试抹成“显著优势”。
- 强制三项价值。
- 没有说明作者为什么在意。

### 合适的改写

> 对我来说，Icon Font 最大的价值还是管理。图标样式以后肯定会改，只要旧 ID 不动，开发替换字体文件就能让所有引用一起更新。文件更小、CSS 更好调当然也有用，但真正让我决定换方案的，是不用再挨个核查不同版本的 SVG。

为什么更合适：

- 保留个人选择的原因。
- 用 ID 和替换文件说明机制。
- 不把三项优点写成同等重要。
- 没有添加俏皮口头禅。

## 2. 清除行业升华

### AI 式

> Figma MCP 与 Cursor 的结合，标志着设计与开发边界的进一步消融。设计稿不再只是静态交付物，而是连接创意与代码的桥梁，推动产品开发进入全新的智能化阶段。

### 合适的改写

> 我真正关心的不是“设计师会不会写代码”，而是设计意图能不能少丢一点。组件名、属性和代码变量如果能提前对齐，AI 拿到的就不只是一张截图，它至少知道哪些差异是设计师故意留下的。

这里允许一次对照，因为它澄清了文章问题；不要在后文继续堆“不是……而是……”。

## 3. 防止 Aaron 模仿秀

### 过度模仿

> Anyway，说白了，这玩意儿真的很土，但又土得很有价值。你以为 Agent 越强越好吗？当然不是。Workflow 才是那个能把一切接住的东西。

问题：

- 口头标记堆叠。
- 凭空提高情绪。
- 用反问制造戏剧性。
- 把比喻当结论。

### 合适的改写

> Agent 能帮团队发现流程，但稳定执行仍然需要显式节点。哪些步骤固定、哪里允许模型判断、什么时候必须人工确认，这些边界只有被写出来，团队才有办法检查和维护。

这段没有显眼口癖，仍然符合核心声音，因为判断具体、带条件，也能落到工作方式。

## 4. 保留认识变化，而不是制造灵魂

### AI 式文化评论

> 《再见绘梨》以独特的电影化分镜深入探讨了真实与虚构的边界，展现了藤本树对虚无主义的深刻思考，带给读者强烈的情感冲击。

### 合适的改写

> 我第一次看时只觉得结尾那场爆炸莫名其妙。重新翻了一遍后，前面那些规整得近乎无聊的四格开始变得可疑：画面越像手持摄影，我越容易相信它是真的，作者也就越方便在“剪辑”里动手脚。

这段能够使用第一人称，是因为原稿明确提供了两次阅读和认识变化。换一篇没有亲历信息的稿子，不得套用这种开头。

## 5. 资讯稿不强行人格化

### 过度改写

> 不愧是 OpenAI，命名又开始整活了。Anyway，这次 1M 上下文确实有点猛，说白了就是模型终于能把工具玩明白了。

### 合适的改写

> GPT-5.4 的上下文扩展到 1M token，同时提高了输入和输出价格。官方称工具搜索能减少模型在大量工具之间做选择的消耗，但一次完整任务是否更便宜，还要看实际 token 用量。

资讯模式只保留有依据的反应。作者的吐槽可以出现一次，但不能覆盖数字与限制。

## 6. 从笔记整理文章

### 输入笔记

```text
试了 Stitch，效果跑偏。
一开始以为是 token 写得不全。
后来换 Claude Code，同一份 Dm 暴露的问题更稳定。
感觉聪明工具会自动补东西，反而不适合验证规范。
```

### 合适的整理

> 我最初用 Stitch 验证 DESIGN.md，结果经常跑偏。那时我以为是 token 写得不够完整，于是继续补颜色、圆角和组件规则，但生成结果并没有因此变得更可预测。
>
> 后来我把同一份 Dm 交给 Claude Code。它生成的页面未必更好看，暴露的问题却稳定得多：圆角没写清楚就会用错，组件分类含糊就会混在一起。到这里我才意识到，聪明工具会替规范补缺口，出效果很方便，却不一定适合验证规范本身。

没有补充产品版本、测试次数或作者情绪，因为笔记没有提供。
